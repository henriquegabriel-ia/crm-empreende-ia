## 1. Objetivo

Uma pessoa que não desenvolve, com um computador Windows (ou macOS), implanta uma instância segura do CRM sozinha, seguindo um guia só, e consegue provar que a instância ficou certa. Para isso:

1. **um guia linear** (`docs/IMPLANTACAO.md`) da conta no Supabase até a equipe usando, que reaproveita os guias que já existem e tem checklist e solução de problemas;
2. **duas conferências que reprovam**: uma no banco (`supabase/instance-check.sql`, colada no editor SQL do painel) e outra na URL publicada (`npm run verify-instance`), que juntas cobrem o que a instância precisa ter ligado;
3. **um ensaio real** do guia por pessoa não desenvolvedora, com roteiro e formulário, até os três marcos da Saída da F1.

## 4. O guia `docs/IMPLANTACAO.md`

### 4.1 Princípios de escrita

- **Para quem não desenvolve.** Cada etapa diz o que a pessoa vai ver na tela e como saber que deu certo. Termos técnicos aparecem uma vez, explicados ("terminal: a janela onde você digita comandos").
- **Windows primeiro.** O comando do Windows vem antes; quando o macOS muda, ele aparece logo abaixo, marcado. O terminal recomendado no Windows é o **Prompt de Comando** (`cmd`), porque o PowerShell, com a política de execução padrão, recusa `npm.ps1` e `npx.ps1`; quem usar o PowerShell lê a saída na solução de problemas (`npm.cmd`, `npx.cmd`). Os comandos de copiar arquivo vêm nas três formas, como o guia provisório já fazia.
- **Marcadores iguais aos do guia provisório.** `<SEU_PROJECT_REF>`, `<SUA_URL>` e `<SEU_REPOSITORIO>`, explicados no topo.
- **Apontar, não duplicar.** Quando já há guia, a etapa traz o resumo de uma a três frases, o que fazer agora e o link com âncora. O guia novo não repete tabelas de outros (a Free × Pro aparece resumida em três linhas, com o link para a completa).
- **Uma conferência no fim de cada bloco.** Depois das migrações, o `instance-check.sql`; depois do Auth, o `verify-instance`; depois do primeiro dono, o `instance-check.sql` de novo.
- **Sem promessa que o CRM não cumpre.** Nada de envio de e-mail pelo CRM, notificação, backup automático no Free ou recuperação de dados excluídos.

### 4.5 A volta atrás e o remédio de emergência (texto do 1.1, no Apêndice A.9)

Os dois casos usam o mesmo comando, no editor SQL: `drop function private.discard_unproven_password(), private.record_email_proof(), private.refuse_email_change_without_org() cascade` ([seção 16.9 do desenho do 1.1](1.1.md#169-caminho-de-atualização), passos 5 e 8). O guia explica, em linguagem simples: o que deixa de valer (a senha anterior à confirmação deixa de ser descartada; a admissão continua fechada, porque o aceite e a criação da empresa passam a exigir a sessão aberta pelo link do e-mail), que depois disso o `instance-check.sql` reprova "Gatilhos" (esperado, até a migração nova que os recria) e que é preciso avisar quem mantém a base. A volta atrás do reforço (passo 5) só serve a quem precisa sair dele por decisão; o remédio de emergência (passo 8), a uma falha de migração do Auth provocada por esses gatilhos.

## 6. `supabase/instance-check.sql`

### 6.1 Geração

- Módulo novo `scripts/lib/instance-check.mjs`, com `renderInstanceCheck(manifest, { demoPipelineId })` puro, sem banco: monta o SQL a partir do manifesto e das listas fixas desta seção. Lança `ManifestError` se um objeto da lista fixa não estiver no manifesto (por exemplo, uma função crítica renomeada), com a instrução de atualizar a lista.
- `scripts/build-base-manifest.mjs` acrescenta o terceiro arquivo à lista de `syncGeneratedFiles` (`INSTANCE_CHECK_FILE = 'supabase/instance-check.sql'`, exportado de `base-manifest.mjs`). O `manifest:build` grava e o `manifest:check` confere, com as mensagens que já existem (`REBUILD_HINT` e `CUSTOM_HINT`, esta com o terceiro caminho no `git checkout`).
- O id do funil "Parcerias" da demonstração vem de `buildDemoDataset()` (`scripts/lib/demo-seed.mjs`), para a linha informativa dos dados de demonstração.
- Cabeçalho do arquivo, em comentários: o que é, "ARQUIVO GERADO por `npm run manifest:build`: não edite à mão", a versão da base (`lastMigration`), que é só leitura, como colar no editor SQL do painel com o papel padrão, como ler o veredito, a diferença para o `db-drift-check.sql` (este compara o banco inteiro; aquele confere o mínimo de segurança de uma instância) e que a configuração do Auth é conferida pelo `npm run verify-instance`.

### 6.2 Forma

Um único `SELECT` com CTEs, sem dependência de funções do CRM:

```sql
with params as (
  select 'postgres'::name as migration_role          -- trocado só pelo test:db (seção 12.2)
), expected_migrations(version, name) as (values ('20260906051319', 'commercial_foundation'), ...),
history_present as (select pg_catalog.to_regclass('supabase_migrations.schema_migrations') is not null as present),
live_migrations as (
  select x.version, x.name
  from history_present h
  cross join lateral pg_catalog.xmltable('/table/row'
    passing case when h.present then pg_catalog.query_to_xml(
      'select pg_catalog.to_jsonb(m)->>''version'' as version, pg_catalog.to_jsonb(m)->>''name'' as name from supabase_migrations.schema_migrations m',
      false, false, '') end
    columns version text path 'version', name text path 'name') x
),
expected_tables(object, rls) as (values ...),          -- tabelas da base com RLS, do manifesto
expected_triggers(object, enabled) as (values ...),    -- os 80 gatilhos, com o estado do manifesto
expected_acl(kind, object, acl) as (values ...),        -- schemas, tabelas, views e funções da base: a ACL dos papéis da API
critical_functions(object, body_hash, security, config) as (values ...),
required_indexes(object) as (values ('public.activities.activities_owner_pending')),
live_acl as (...),                                     -- a mesma regra de private.base_acl, escrita na consulta
checks as (... uma linha por verificação ...),
infos as (... linhas de informação ...)
select resultado, verificacao, detalhe from (...) r order by ordem, verificacao collate "C";
```

- `query_to_xml` só é chamado com o histórico presente (o `case` não avalia o ramo falso); sem ele, `xmltable` não devolve linhas. `to_jsonb(m)` tolera um histórico sem a coluna `name` (como `private.base_fingerprints()` já faz).
- O nome das funções no catálogo é lido como `p.oid::regprocedure::text`, a mesma forma do manifesto; o corpo, como `coalesce(nullif(p.prosrc, ''), pg_get_function_sqlbody(p.oid))` e o hash, como `left(encode(sha256(convert_to(replace(<corpo>, E'\r\n', E'\n'), 'UTF8')), 'hex'), 16)`, as mesmas regras do manifesto (seção 4.5 do desenho do 1.13).
- A ACL ao vivo segue a regra de `private.base_acl`: `aclexplode` da ACL (ou de `acldefault`), só `PUBLIC`, `anon`, `authenticated` e `service_role`, sem `MAINTAIN`, letras na ordem `arwdDxtXUCTc`, papéis em ordem C. O `test:db` compara as duas num banco recém-migrado (as mesmas cadeias para todos os objetos da base).
- Tamanho estimado: cerca de 25 KB (80 gatilhos, cerca de 120 ACLs, 20 migrações e 13 funções críticas), longe do limite do editor; o AC-5 reprova acima de 100 KB.
- Nada é escrito: sem tabela temporária nem função volátil com efeito. A única exceção ao "sem `set_config`" do desenho é o `search_path` vazio, só na transação, para o texto das políticas sair como o do manifesto (seção 21, ajuste 15): ele não grava nada.

### 6.4 Por que não reaproveitar `private.base_fingerprints()`

O roteiro deixa a escolha aberta ("pode reaproveitar"). Chamar a função numa consulta comum falha na análise quando ela não existe, e ela só existe a partir de `20261019110000_update_protection.sql`: a conferência pararia com "function does not exist" justamente na instância com migrações faltando, que é o caso que ela precisa explicar. Ler o catálogo direto mantém a consulta pequena (cerca de 25 KB contra os 202 KB do drift check) e independente da versão. O custo é repetir em SQL duas regras do manifesto (hash do corpo e ACL), que o `test:db` amarra às da função (seção 12.2, item 2).

## 7. `npm run verify-instance`

### 7.1 Arquivos

- `scripts/verify-instance.mjs`: a linha de comando (argumentos, leitura das variáveis, impressão e código de saída).
- `scripts/lib/verify-instance.mjs`: a regra, pura e testável: `verifyInstance({ siteUrl, supabaseUrl, publishableKey, fetch, config, timeoutMs, allowLocal })` devolve `{ checks: [{ status: 'ok' | 'fail' | 'warn', title, detail }], approved }`, mais `keyProblem(key)`, `instanceInputs(argv, env, files)`, `formatVerifyReport(result)` e `headerProblems(expected, received)`.
- `scripts/lib/verify-instance.d.mts`: tipos para o E2E em TypeScript, como `security-headers.d.mts`.
- `package.json`: `"verify-instance": "node scripts/verify-instance.mjs"`.

Sem dependência nova: `fetch` e `AbortSignal.timeout` do Node 20+.

### 7.2 Entradas

| Valor | Ordem de leitura |
| --- | --- |
| `<SUA_URL>` | 1º argumento posicional; senão `SUPABASE_AUTH_SITE_URL` lida por `loadAuthEnv` (o `supabase/.env` do `config:check`). |
| URL do Supabase | `--supabase-url`; senão `VITE_SUPABASE_URL` do ambiente, de `.env.local` ou de `.env` na raiz (lidos com `readDotenv`). |
| Chave pública | `--key`; senão `VITE_SUPABASE_PUBLISHABLE_KEY` na mesma ordem. |

Recusas antes de qualquer pedido (saída 2, com a instrução):

- chave começando com `sb_secret_`, ou JWT cujo `payload.role` seja `service_role` ou `supabase_admin` ("Esta é a chave secreta… Use a chave pública (`sb_publishable_…`). Se ela foi colada em algum arquivo do repositório, troque-a no painel.");
- `<SUA_URL>` sem `https://`, com caminho, consulta ou barra no fim (as mesmas regras da Site URL do `config:check`, reaproveitadas), salvo `--local`, que aceita `http://localhost:<porta>` e `http://127.0.0.1:<porta>` (ensaio contra o `npm run preview`) e marca o relatório como "ensaio local, não vale como conferência da instância publicada";
- URL do Supabase sem `https://` (salvo `--local`).

A chave aparece na saída só como os 12 primeiros caracteres seguidos de "…".

### 7.5 Comparação dos cabeçalhos

- Nomes sem diferença de maiúsculas; valores com os espaços normalizados.
- Quando a plataforma junta duas ocorrências do mesmo cabeçalho numa só, separadas por vírgula (a Vercel pode mandar o próprio `strict-transport-security` além do do `vercel.json`), a conferência aceita se uma das partes for igual à esperada e nenhuma for mais fraca. No `Strict-Transport-Security`, compara as diretivas: `max-age` maior ou igual, `includeSubDomains` presente.
- A CSP é comparada por diretiva (`parseCsp`), na mesma ordem de fontes não exigida: uma fonte a mais (por exemplo, um host acrescentado só na Vercel) reprova, porque o repositório é a fonte da regra.
