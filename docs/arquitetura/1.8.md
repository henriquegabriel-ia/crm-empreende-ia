## 4. Regras para IA (`AGENTS.md` e `CLAUDE.md`)

### 4.1 Por que um arquivo só

Codex e Cursor leem `AGENTS.md`; o Claude Code lê `CLAUDE.md` e aceita importar outro arquivo com `@caminho`. Duas cópias dos invariantes divergiriam na primeira mudança. `CLAUDE.md` fica assim (em pt-BR, como o resto):

```markdown
# CRM — instruções para o Claude Code

As regras deste repositório estão em AGENTS.md, importado abaixo. Leia antes de mudar qualquer arquivo.

@AGENTS.md
```

Não confundir com o `CLAUDE.md` global do dono (`~/.claude/CLAUDE.md`, do framework AIOX): ele não vai para o repositório e não é citado.

### 4.3 Invariantes (conteúdo mínimo)

**Banco e migrações**

- Migração só como arquivo novo, com data e hora posteriores à última; nunca editar nem apagar uma migração existente, nem "consolidar" o esquema. Migração de quem personaliza: `<data e hora>_custom_<nome>.sql`.
- Aditiva e segura com dados: backfill testado em `supabase/tests/upgrade/<migração>.sql` (na base).
- Toda tabela de dados em `public` tem `org_id`, `unique (id, org_id)`, FK composta `(<id>, org_id)` para as tabelas da base, RLS ligada e políticas com `org_id = (select private.current_org())` e `private.can_write()` / `private.can_manage()`. Nunca `profiles.org_id` direto.
- Permissões sempre explícitas: desde `20261019120000_default_privileges.sql`, objeto novo nasce sem permissão para a API. Tabela: `revoke all ... from public, anon, authenticated, service_role` e `grant` do mínimo para `authenticated` (e `select, insert, update, delete` para `service_role` se uma integração do servidor gravar nela). Função chamada pela API: `grant execute ... to authenticated`. Sem o `grant`, o PostgREST responde 42501.
- Função em `private`: `security definer` só quando precisa, sempre `set search_path = ''` e nomes qualificados; RPC em `public`: `security invoker`, chamando a privada. Nenhuma função de `private` executável por `anon` além de `instance_status`.
- Regra própria só por gancho `private.custom_*` ou objeto `custom_*`; nunca editar função, política ou gatilho da base; nunca remover nem recriar um gancho; nunca criar objeto da base com o prefixo `custom_`.
- Migração da base que recria ou remove função, gatilho ou política da base começa com `select private.assert_base_definition(...)` com o hash do manifesto anterior (o teste reprova a guarda esquecida; SQL dinâmico fica na revisão). Depois de mudar o schema: `npm run gen:types` e `npm run manifest:build`, com os arquivos gerados no commit. Nunca rodar `manifest:build` para "consertar" uma diferença numa instância personalizada.
- Gatilho novo que lê outra tabela é `security definer` ou não cita `private.*`.
- Toda tabela ou coluna nova da base em `public` entra em `DEMO_SCHEMA` (`scripts/lib/demo-seed.mjs`), seguida de `npm run seed:demo`; migração que grava linhas num projeto novo entra em `RESTORE_SEEDED_TABLES`.
- Coluna nova em `deals` editada pelo formulário entra em `save_deal` (`SAVE_DEAL_CREATE_FIELDS`, `SAVE_DEAL_EDIT_FIELDS` e a RPC). Responsável novo numa tabela nova entra em `portfolio_counts`, `move_member_portfolio` e `refuse_inactive_assignee`; regra de papel em `role_change_allowed`.

**Acesso e Auth**

- Entrada só por convite (`create_invitation`); nenhum `insert` em `organizations` fora de `private.provision_organization`; a conta só ganha papel por `accept_invitation` ou `create_workspace`, com a prova do e-mail (`private.email_proven`); não remover nem contornar `discard_unproven_password` e `record_email_proof`.

## 6. Privilégios padrão revogados

### 6.1 Migração `20261019120000_default_privileges.sql`

Aditiva, sem linha de dado, sem backfill (sem arquivo em `supabase/tests/upgrade/`), sem objeto novo em `public`. Nesta ordem:

```sql
-- 1. A guarda do 1.13: base_fingerprints é recriada abaixo.
select private.assert_base_definition('function', 'private.base_fingerprints()', array['936e6d247f4dee1e']);

-- 2. Daqui em diante, o que postgres criar em public nasce sem permissão para a API (todos os privilégios, não só DML).
alter default privileges for role postgres in schema public revoke all on tables from anon, authenticated, service_role;
alter default privileges for role postgres in schema public revoke all on sequences from anon, authenticated, service_role;
alter default privileges for role postgres in schema public revoke all on functions from anon, authenticated, service_role;
-- O EXECUTE de PUBLIC é padrão global do PostgreSQL: só sai sem "in schema", e vale para funções novas em qualquer schema.
alter default privileges for role postgres revoke execute on functions from public;

-- 3. A service_role com o que a API usa, explícito (antes vinha só dos privilégios padrão, e falta nos projetos novos).
grant select, insert, update, delete on table public.activities, public.audit_logs, ... (as 23) to service_role;
revoke truncate, references, trigger on table public.activities, ... (as 23) from service_role;
revoke execute on function public.accept_invitation(uuid), ... (as 18) from service_role;

-- 4. base_fingerprints com o tipo default_acl (seção 6.4); mesma assinatura, mesmo revoke.
create or replace function private.base_fingerprints() ...
```

- `for role postgres`: é o papel que aplica as migrações no Supabase hospedado (`db push`) e no cluster embutido (`scripts/lib/embedded-db.mjs`). Os privilégios padrão de `supabase_admin` ficam como estão (`postgres` não pode alterá-los; seção 14).
- `revoke all on functions ... in schema public` tira o que o Supabase acrescenta para os papéis da API; o `revoke execute ... from public` sem schema é o que efetivamente fecha a função nova (o relato da comunidade no changelog: a forma com `in schema public` não tem efeito sobre `PUBLIC`).
- Nada muda nos objetos que já existem: privilégio padrão só vale para objeto criado depois. As migrações da base já concedem tudo de forma explícita, e o passo 3 iguala a `service_role`.
- A lista das 23 tabelas e das 18 funções é a do manifesto de hoje (seção "Base estudada"); o teste de convergência (AC-10) é o juiz: se faltar ou sobrar um objeto, um dos três bancos diverge.

### 6.2 Por que também `service_role`, `TRUNCATE` e as funções

- **`service_role` nos privilégios padrão**: como a documentação do Supabase. Ela ignora a RLS; uma tabela nova aberta para ela por padrão é uma tabela que uma Edge Function com a chave grava sem ninguém ter decidido. Com o padrão revogado, quem integra concede de propósito.
- **`TRUNCATE`, `REFERENCES`, `TRIGGER`**: `TRUNCATE` ignora a RLS; `REFERENCES` deixa uma conta criar FK que trava exclusões; `TRIGGER` deixa criar gatilho na tabela. Nenhum é usado pela API, e o revoke documentado pelo Supabase não os cobre.
- **Funções**: uma função `SECURITY DEFINER` nova em `public` sem `revoke` é executável por `anon` pelo `PUBLIC`. Com o padrão global revogado, nasce fechada em qualquer schema; o PostgREST devolve 42501 com a dica do `GRANT`.

### 6.3 `service_role`: a escolha das permissões explícitas

| Opção | Efeito | Escolha |
| --- | --- | --- |
| Conceder `arwdDxt` como hoje | Projetos novos iguais aos antigos, mas mantém `TRUNCATE`, `REFERENCES` e `TRIGGER` sem uso | Não |
| **Conceder `arwd` nas tabelas e tirar o `EXECUTE` das RPCs** | Projetos antigos perdem quase só o que nunca foi usado (17 das 18 RPCs de `public` chamam funções de `private` sem permissão para a `service_role`, então nunca funcionaram por essa chave; `search_crm` é SQL só sobre tabelas de `public` e funcionava por ela, ignorando a RLS, e deixa de funcionar, correção da revisão na seção 20; `instance_status` continua para `anon` e `authenticated`); integrações e os ganchos do 1.13 continuam gravando pela chave | **Sim** |
| Não conceder nada à `service_role` | Mínimo, mas quebra o caminho de integração do servidor previsto (receptor da Fecha IA) e a decisão do 1.13 de a chave continuar gravando | Não |

Os testes do 1.13 que gravam como `service_role` (`customization.sql`) continuam valendo e passam a provar a permissão explícita.

### 6.4 Manifesto e conferência

`private.base_fingerprints()` ganha o tipo `default_acl`, com nove linhas fixas (emitidas mesmo sem linha em `pg_default_acl`), para o papel `postgres` (`to_regrole('postgres')`; sem ele, nenhuma linha):

| `object` | Leitura |
| --- | --- |
| `postgres/*/tables`, `postgres/*/sequences`, `postgres/*/functions` | o padrão global (`defaclnamespace = 0`); sem linha, `acldefault(<tipo>, postgres)` (funções: `PUBLIC=X`) |
| `postgres/public/tables`, `.../sequences`, `.../functions` | o acréscimo do schema `public`; sem linha, vazio |
| `postgres/private/tables`, `.../sequences`, `.../functions` | o acréscimo do schema `private`; sem linha, vazio |

`props = {"acl": private.base_acl(...)}`, só com os papéis da API, como nos demais objetos (o `MAINTAIN` fica de fora pela regra do 1.13). Depois da migração, as nove ficam com `acl` vazio. `parent` nulo, `body_hash` nulo.

`scripts/lib/base-manifest.mjs`: `KINDS` ganha `default_acl`; o check gerado ganha o rótulo `privilégio padrão` e a regra: `default_acl` com hash diferente é **alterado, atenção**, com o detalhe "Objetos novos criados por postgres em public nascem com permissões para anon (select): uma tabela esquecida sem RLS ficaria aberta pela API. Para fechar: alter default privileges for role postgres in schema public revoke all on tables from anon, authenticated, service_role;" (o comando certo para cada linha). Como as linhas são fixas, não há "ausente" nem "extra" desse tipo. O formato do manifesto continua `1` (um tipo a mais não muda a forma do arquivo).

A regra de extras do 1.13 (seção 21) segue igual: uma tabela extra sem RLS só vem com atenção se tiver permissão para `anon`, `authenticated` ou `PUBLIC` — com o padrão revogado, isso só acontece por um `grant` de alguém.

## 7. Spike: Lovable com Supabase externo

Resultado registrado em `docs/PERSONALIZAR/LOVABLE.md`, com a data da consulta e os links. Nenhuma conta criada; a parte prática é pendência humana (seção 7.5).

### 7.1 Viabilidade (pela documentação de 19/10/2026)

- **Trazer o CRM para o Lovable**: o Git sync é só de exportação; conectar cria um repositório novo. O caminho possível é criar o projeto no Lovable, conectar o GitHub e enviar o código do CRM ao branch sincronizado (commits de qualquer ferramenta entram no Lovable, sem force-push). A documentação não diz se aceita um histórico sem relação com o do repositório criado. Isso convive mal com a D5 (clonar o repositório do programa e registrar `upstream`): o repositório do aluno passa a ser o criado pelo Lovable, e a atualização vira `git pull upstream` num clone local seguido de push para ele.
- **Conectar um Supabase próprio**: possível, ligando uma **organização** Supabase ao workspace do Lovable e escolhendo o projeto. O Lovable Cloud vem ligado por padrão e precisa ser recusado.
- **Banco**: o Lovable escreve o SQL, pede aprovação no chat, executa no projeto conectado e salva o arquivo em `supabase/migrations/`. Não está documentado como nomeia o arquivo nem se registra a versão em `supabase_migrations.schema_migrations`.
- **Tipos**: o Lovable regenera "os tipos que o app usa", sem dizer o caminho; o CRM usa `src/integrations/supabase/database.types.ts`, gerado pelo `gen:types`.

### 7.2 Riscos

| Risco | Por quê | Mitigação |
| --- | --- | --- |
| Sobrescrever ou "consolidar" o schema | O legado `.lovable/` mandava apagar as migrações e pôr um esquema único; um agente pode propor de novo | `AGENTS.md` (no conhecimento do projeto do Lovable); revisar todo SQL antes de aprovar; recusar `drop`, `create or replace` fora de `custom_*` e qualquer mudança em `supabase/migrations/` existentes; o CI (`manifest:check`, regras de migração) reprova no push |

| SQL aplicado fora do `db push` | O arquivo e o banco podem divergir; o histórico pode não registrar a versão | Conferência de drift depois de cada mudança; preferir `npx supabase db push` |
| Acesso à organização Supabase inteira | O Lovable passa a enxergar e alterar todos os projetos da organização ligada, inclusive o da empresa com dados reais | Nunca ligar a organização da instância de produção; usar um projeto de desenvolvimento numa organização Supabase à parte |
| Segredos compartilhados | Vários projetos do Lovable num mesmo Supabase sobrescrevem os segredos uns dos outros | Um projeto Supabase por projeto do Lovable |
| Gerenciador de pacotes | O Lovable historicamente grava `bun.lockb`; a base usa só npm (D1) e a Vercel escolhe pelo arquivo de trava | Conferir e apagar `bun.lock`/`bun.lockb`; a regra está em "Não tocar" |
| Tipos paralelos | Um segundo arquivo de tipos gerado pelo Lovable diverge do `database.types.ts` | Rodar `npm run gen:types`; o `gen:types:check` do CI aponta |
| Privilégios padrão | Tabelas criadas pelo Lovable sem `grant` respondem 42501 (depois deste item e de 30/10/2026 em todo projeto) | Esperado e seguro: o guia mostra o `grant` e a RLS |
| Funções que dependem do Lovable Cloud | Visualizações de backend, login social e outros recursos só existem no Cloud | Ficam fora; o CRM não depende deles |

### 7.3 Recomendações

1. Caminho principal para alunos: Claude Code, Codex ou Cursor no clone do repositório, lendo o `AGENTS.md`.
2. Lovable, se o aluno insistir: **só para telas**, sem Supabase conectado (o app aponta para o Supabase pelas variáveis `VITE_SUPABASE_URL` e `VITE_SUPABASE_PUBLISHABLE_KEY` de sempre); as mudanças no banco vêm como migrações `_custom_` escritas no repositório e aplicadas com `npx supabase db push`, depois da revisão.
3. Se conectar o Supabase: só um projeto de desenvolvimento, numa organização Supabase à parte; renomear cada migração gerada para `_custom_`; rodar a conferência de drift; nunca aprovar SQL que toque objetos da base.
4. Colar o resumo do `AGENTS.md` no conhecimento do projeto do Lovable (o guia traz o texto curto pronto).

### 7.4 O que fica fora

Suporte oficial ao Lovable como ferramenta de implantação; qualquer ajuste da base para o Lovable (nome de migração, caminho dos tipos) antes do ensaio prático.

### 7.5 Pendência humana (ensaio prático, com conta do programa)

Num projeto Supabase de desenvolvimento numa organização à parte e numa conta Lovable do programa: enviar o código do CRM ao repositório criado pelo Lovable (aceita o histórico?), conferir se o build passa com npm e se aparece `bun.lockb`; pedir uma tabela nova e anotar o nome do arquivo de migração, se a versão entra em `schema_migrations`, se vem `grant` e RLS, e o caminho dos tipos regenerados; pedir algo que tente mudar uma função da base e ver se o Lovable respeita o `AGENTS.md` colado no conhecimento; rodar a conferência de drift no fim; registrar em `LOVABLE.md` e decidir se a recomendação muda.

## 8. Modelo de dados e RPCs

Sem tabela, coluna, índice, política ou RPC nova. Muda:

- `pg_default_acl` do papel `postgres` (seção 6.1);
- as permissões da `service_role` nas 23 tabelas e nas 18 funções de `public` (seção 6.3);
- `private.base_fingerprints()`, mesma assinatura (`returns table(kind text, object text, parent text, props jsonb, body_hash text, hash text)`), mesmo `security invoker`, `stable`, `search_path = ''` e o mesmo `revoke` de todos os papéis da API.

O tipo gerado da base não muda (nada em `public` é criado; permissões não entram no tipo); o `DEMO_SCHEMA` e `RESTORE_SEEDED_TABLES` não mudam.

## 9. Fluxos

Sem tela nova no app.

1. **Aluno personaliza com IA**: abre o repositório na ferramenta → a IA lê `AGENTS.md` → segue `docs/PERSONALIZAR/` com o exemplo como molde → migração `_custom_` (com `grant` e RLS) → `npx supabase db push` no projeto de desenvolvimento → `npm run gen:types` → código em `src/custom/` e a linha marcada `custom:` nas telas da base → Ajuda → a suíte → publicar.
2. **Tabela esquecida sem permissões**: criada pelo editor SQL, pelo Lovable ou por migração → a API responde 42501 (com a dica do `GRANT`) → quem personaliza decide o `grant` e a RLS. Nenhum dado fica exposto no meio-tempo.
3. **Mantenedor da base cria tabela nova (F2A)**: `revoke` + `grant` explícitos (inclusive `service_role`), RLS, `gen:types`, `manifest:build`; o `test:db` mostra 42501 se esqueceu.
4. **Atualização de uma instância existente**: `db push` aplica a migração → a guarda passa (ou para, se `base_fingerprints` foi alterada à mão) → a conferência mostra as nove linhas `default_acl` em dia.

## 10. Casos de borda e corrida

- **Projeto criado depois de 30/05/2026 (padrão já revogado para DML)**: a migração completa o revoke (`TRUNCATE`, `REFERENCES`, `TRIGGER`, funções) e concede a `service_role`; a impressão digital fica igual à dos antigos (AC-10).
- **A mudança do Supabase de 30/10/2026 chega depois da migração**: ela revoga o que já não existe; nenhum efeito. Se ela, por algum motivo, conceder de volta algo ao `postgres`, a conferência acusa nas linhas `default_acl`.
- **Objeto criado por `supabase_admin` em `public`** (recursos da plataforma, eventualmente o painel): continua com os privilégios padrão dele. Fora do alcance de `postgres`; a conferência de drift marca com atenção uma tabela extra sem RLS aberta para a API, venha de onde vier.
- **Extensão criada depois por `postgres`** (por exemplo, `pg_trgm` num schema próprio): as funções dela nascem sem `EXECUTE` para `PUBLIC` se o script da extensão rodar como `postgres`; usar uma delas numa política ou RPC chamada pela API pede `grant execute ... to authenticated`. O `AGENTS.md` e [Entidade nova](../PERSONALIZAR/ENTIDADE.md) dizem isso; o 42501 do PostgreSQL não traz a dica do `grant`. No Supabase, o `supautils` pode instalar uma extensão privilegiada como `supabase_admin`, e aí o privilégio padrão de `postgres` não vale: o comportamento depende de quem fica dono dos objetos da extensão, e o `test:db` (tudo como `postgres`) pode divergir da plataforma. As migrações da base não criam extensões.
- **Função de gatilho nova**: o `EXECUTE` só é conferido na criação do gatilho (pelo dono da tabela), não quando ele dispara; os gatilhos continuam funcionando sem `grant`.
- **`create or replace` de função existente**: mantém as permissões que ela já tinha; o padrão só vale para função nova (ou recriada com `drop`).
- **Função usada numa política**: chamada com o papel de quem consulta; função nova exige `grant execute` para `authenticated` (as atuais, `current_org`, `can_write` e `can_manage`, já têm).
- **Migração aplicada por outro papel** (alguém rodando pelo editor como outro usuário): os objetos dele seguem os padrões dele. O Supabase usa `postgres` no editor e no `db push`; o guia diz para não trocar o papel do editor.
- **`base_fingerprints` alterada à mão**: a guarda para a migração com os dois caminhos do 1.13.
- **Banco sem o papel `postgres`** (não acontece no Supabase nem no cluster): as linhas `default_acl` não saem, e a conferência mostra as nove como ausentes (atenção).
- **Corrida**: a migração roda numa transação do `db push`; `alter default privileges` e `grant` pegam travas de catálogo curtas, sem reescrever tabela. Gravações concorrentes não são afetadas.

## 11. Caminho de atualização para instâncias existentes

A migração não toca em linha nenhuma, não reescreve tabela e não dispara gatilho. Em instâncias antigas (privilégios padrão antigos): a `service_role` perde `TRUNCATE`, `REFERENCES` e `TRIGGER` nas tabelas e o `EXECUTE` das RPCs de `public` (sem uso, seção 6.3); objetos que a instância criar depois nascem fechados. Objetos extras já criados pelo aluno ficam como estão (o privilégio padrão não é retroativo); a conferência de drift já mostra com atenção os que estão abertos para a API.

O frontend do mesmo commit não depende da migração. No projeto do dono, ela entra na lista de pendentes do registro do ambiente do dono, por último, depois de `20261019110000_update_protection.sql`; depois de aplicada, a conferência deve mostrar as nove linhas `default_acl` em dia (sem linha de diferença) e, entre os extras, as tabelas do Instagram e da entrada de leads com as permissões que já têm (as que estiverem sem RLS e abertas continuam com atenção, como hoje). O receptor da Fecha IA passa a ser a 21ª migração e precisa de `grant` explícito para a `service_role` ([Integrações pendentes](../INTEGRACOES-PENDENTES.md)).

## 12. Alternativas consideradas

| Alternativa | Por que não |
| --- | --- |
| Duas cópias dos invariantes (`AGENTS.md` e `CLAUDE.md`) | Divergem na primeira mudança; o Claude Code importa o outro arquivo. |
| Regras por ferramenta (`.cursor/rules`, `.github/copilot-instructions.md`) | Cursor e Codex já leem `AGENTS.md`; mais arquivos, mais rot. Fica para quando houver pedido. |
| `AGENTS.md` longo, com todo o detalhe | A IA lê melhor uma lista curta com ponteiros; o detalhe já mora nos guias e nos desenhos, que os testes mantêm. |
| Exemplo só como texto no guia | Fica velho sem ninguém ver; o pedido é "passa na suíte". |
| Exemplo dentro de `src/` (rota real no app) | Entregaria uma tela de contratos a toda empresa, com tabela que a base não tem. |
| Gerar os tipos do exemplo só dentro do teste | O aluno vê no guia o tipo que vai ganhar; o arquivo versionado e o `gen:types:check` mostram a diferença quando a base muda. |
| Ponto de extensão novo na base para rotas, menu e Ajuda | É o registro de módulos do 2B.12; antecipar aqui seria meio desenho. A mudança mínima marcada `custom:` resolve até lá. |
| Só o revoke documentado pelo Supabase (DML em `public`) | Deixa `TRUNCATE` (ignora RLS), `REFERENCES`, `TRIGGER` e o `EXECUTE` de `PUBLIC` nas funções. |
| `revoke execute on functions from public` dentro de `in schema public` | Sem efeito: o padrão de schema só acrescenta ao global. |
| Não mexer nos privilégios padrão e confiar na conferência | A conferência só ajuda depois, e só se alguém rodar; a tabela esquecida fica aberta no meio-tempo. |
| Um gatilho de evento (`event trigger`) que recusa `create table` sem RLS | Exige superusuário no Supabase (não disponível para `postgres`) e quebraria o padrão "cria a tabela, depois liga a RLS" das migrações. |
| Mover a API para um schema `api` dedicado | Mudança grande em toda a base e nas instâncias; fora do item. |
| Manter `arwdDxt` da `service_role` | Igualaria os projetos, mas com privilégios sem uso (seção 6.3). |
