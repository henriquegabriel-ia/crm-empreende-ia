### 4.3 Pro também liga o backup

As cópias diárias do Pro ficam na mesma conta e somem com o projeto; uma conta invadida, um projeto excluído por engano ou um atraso de pagamento (que pausa os projetos e volta a organização ao Free) leva o CRM e as cópias juntos. O guia recomenda, também no Pro, ligar o workflow: é a cópia fora do Supabase. A restauração do Pro pelo painel continua sendo o caminho mais simples para voltar a um dia recente no mesmo projeto; o `backup:restore` é o caminho para um projeto novo, inclusive em outra conta.

## 5. Backup: o workflow modelo

### 5.1 Arquivo e gatilhos

`.github/workflows/backup-banco.yml`, nome "Backup do banco":

- `on: schedule` às 05:30 UTC (02:30 em Brasília, longe do expediente e do CI noturno das 06:00) e `workflow_dispatch` (para rodar na hora, por exemplo antes de uma atualização da base, 1.7b). Sem `push` nem `pull_request`: um fork ou um pull request nunca dispara o dump.
- `permissions: contents: read`; `concurrency: { group: backup-banco, cancel-in-progress: false }` (duas execuções não correm juntas e nenhuma é cortada no meio).
- Um job, `backup`, com `if: vars.CRM_BACKUP_ENABLED == 'true'`, `runs-on: ubuntu-24.04` e `timeout-minutes: 30`. Sem a variável, o agendamento dispara e o job aparece como pulado, sem gastar minutos. É o "desligado por padrão": no repositório da base e em todo clone novo, nada roda até a empresa ligar.
- Por que não um arquivo-modelo fora de `.github/workflows/` para copiar: a cópia ficaria defasada das correções da base e esbarraria na proteção de atualização (o aluno teria um arquivo da base editado). Por que não comentar o `schedule`: ligar exigiria editar o arquivo da base, com o mesmo problema.

### 5.2 Secrets e variáveis

| Nome | Tipo | Para quê |
| --- | --- | --- |
| `CRM_BACKUP_ENABLED` | variável | `true` liga o job; qualquer outro valor, ou ausente, deixa desligado. |
| `CRM_BACKUP_DB_URL` | secret | A conexão do *Session pooler* do projeto (Connect → Session pooler), com a senha do banco no lugar de `[YOUR-PASSWORD]`, codificada para URL (o CLI exige; o guia mostra os caracteres que precisam de `%XX`). A conexão direta `db.<ref>.supabase.co` só tem IPv6 sem o add-on, e o runner do GitHub não tem IPv6: o job recusa com essa explicação. |
| `CRM_BACKUP_PASSWORD` | secret | A senha do `.7z`, com pelo menos 16 caracteres, gerada num gerenciador de senhas e guardada pelo Dono fora do repositório e fora de conversas. Sem ela, o backup não abre. |
| `CRM_BACKUP_RETENTION_DAYS` | variável | Dias que o artefato fica no GitHub, de 1 a 90; padrão 7. |
| `CRM_BACKUP_REMOTE` | variável | Opcional: destino do `rclone`, `<remoto>:<pasta>` (seção 5.6). |
| `CRM_BACKUP_RCLONE_CONFIG` | secret | Opcional: o conteúdo do `rclone.conf` com o remoto acima. |

O primeiro passo do job (`Conferir configuração`, só `bash`, sem conectar no banco) recusa: repositório público (`github.event.repository.private` falso: num repositório público, qualquer pessoa com conta no GitHub baixaria o artefato, e o agendamento seria desligado depois de 60 dias sem atividade); secret ausente; URL sem `postgresql://` ou `postgres://`; host `db.*.supabase.co`; senha curta; retenção inválida; `CRM_BACKUP_REMOTE` sem `CRM_BACKUP_RCLONE_CONFIG` (e o contrário). Os secrets nunca vão para a linha de comando de um `echo`; o GitHub mascara os valores no log.

### 5.3 O dump

`supabase/setup-cli@v1` com `version: 2.119.0` (o Vitest prende essa versão a `SUPABASE_CLI_VERSION`; trocar uma sem a outra reprova). O runner do GitHub tem Docker, que o CLI usa para rodar o `pg_dump` da imagem do Supabase: quem implanta não precisa de Docker. Tudo em `$RUNNER_TEMP/crm-backup`, com `umask 077`, fora da pasta do repositório:

1. `history-before.sql`: `supabase db dump --db-url "$URL" --data-only --schema supabase_migrations -f history-before.sql`.
2. `data.sql`: `supabase db dump --db-url "$URL" --data-only -f data.sql -x storage.buckets_vectors -x storage.vector_indexes -x auth.sessions -x auth.refresh_tokens -x auth.mfa_amr_claims -x auth.one_time_tokens -x auth.flow_state`. **Sem `--use-copy`**: o CLI grava `INSERT` com as colunas (`--column-inserts --rows-per-insert 100000`), que a ferramenta da seção 6 executa sem `psql`. O CLI já abre o arquivo com `SET session_replication_role = replica;` (gatilhos desligados na carga) e fecha com `RESET ALL;`, e comenta as linhas `\restrict` do `pg_dump` novo. Um `pg_dump` lê todas as tabelas numa fotografia só, então os dados são coerentes entre si mesmo com a equipe gravando.
3. `history.sql`: o mesmo comando do passo 1. Se diferir de `history-before.sql`, o job falha: "Uma migração foi aplicada durante o backup. Rode o backup de novo." (os dados poderiam estar no formato de um histórico e o arquivo dizer outro).
4. `schema.sql` (`supabase db dump`) e `roles.sql` (`--role-only`): para diagnóstico e para quem precisar comparar; a restauração não os usa (seção 6.1). O CRM não cria papéis; `roles.sql` só traz papéis criados à mão.
5. Conferência mínima: `data.sql` tem `INSERT INTO "public"."organizations"` e `history.sql` tem pelo menos uma versão; senão, falha ("o backup saiu vazio: confira a conexão").
6. `backup-info.json`, por `jq`: `{ "format": 1, "createdAt": "<UTC ISO>", "commit": "<github.sha>", "repository": "<owner/repo>", "cliVersion": "2.119.0", "files": { "<nome>": { "bytes": n, "sha256": "…" } } }`. O commit é uma pista da versão; a verdade é o `history.sql`.

O que fica de fora, e o guia diz: objetos do Storage (o CRM ainda não usa; 2B.15 e 3.5 vão precisar de outra cópia), segredos do Vault (o CRM não usa), a configuração do Auth (vem do `supabase/config.toml` pelo `config:push`), as variáveis da Vercel e as sessões.

### 5.4 Fidelidade ao CLI

O `--dry-run` do CLI 2.119.0 imprime o script que ele roda. Para os dados: `pg_dump --data-only --quote-all-identifier --role "postgres" --exclude-schema "<lista>" --exclude-table "auth.schema_migrations" --exclude-table "storage.migrations" --exclude-table "supabase_functions.migrations" --schema "*" --column-inserts --rows-per-insert 100000`, com o `sed` do `\restrict`, o `SET session_replication_role = replica;` antes e o `RESET ALL;` depois; a lista de schemas excluídos dos dados inclui `supabase_migrations`, `extensions`, `realtime`, `vault`, `graphql` e outros, e **não** inclui `auth`, `storage`, `private` nem `public`. Para o schema: `--schema-only` com `auth`, `storage` e `supabase_migrations` entre os excluídos. Essas opções ficam em `scripts/lib/backup-dump.mjs` (`CLI_DATA_DUMP`, com a versão do CLI), usadas pelo ensaio (seção 7) e conferidas contra o `--dry-run` real com `--check-cli` (no job `restauracao` do CI, que tem rede): uma atualização do CLI que mude as opções reprova o CI até alguém atualizar a constante e rodar o ensaio.

### 5.5 Cifra, artefato e retenção

- `7z a -t7z -mhe=on -mx=9 -p"$CRM_BACKUP_PASSWORD" "crm-backup-<AAAAMMDD-HHMM>-UTC.7z" <arquivos>` (instala `p7zip-full` se faltar). AES-256 com o nome dos arquivos cifrado. No Windows, o [7-Zip](https://www.7-zip.org/) abre com a senha (botão direito → 7-Zip → Extrair); no macOS, `brew install sevenzip` ou o Keka.
- Depois de cifrar, o job apaga os `.sql` e o `.json` do runner (o runner é descartável, mas um passo seguinte com falha não deve encontrar texto claro).
- `actions/upload-artifact@v7` só do `.7z`, com `retention-days` da variável validada, `compression-level: 0` (já comprimido) e `if-no-files-found: error`.
- Quem baixa: qualquer pessoa com acesso de leitura ao repositório (documentação do GitHub). Por isso: repositório privado (o job recusa público), só as pessoas necessárias como colaboradoras e a senha só com o Dono e quem ele designar.
- Espaço e minutos: o plano Free do GitHub inclui 500 MB de armazenamento de artefatos (somado ao Packages) e 2.000 minutos por mês em repositório privado. O CRM de um time de até 50 pessoas cabe em poucos MB comprimidos; 7 cópias diárias ficam muito abaixo de 500 MB. Cada execução leva alguns minutos (baixar a imagem do `pg_dump` é a maior parte): cerca de 30 a 120 minutos por mês.
- Avisos de falha: o GitHub avisa por e-mail as falhas de um workflow agendado a quem criou o workflow ou a quem o religou. Num repositório clonado, essa pessoa é quem escreveu o arquivo na base; o guia manda **desativar e reativar o workflow** na aba Actions depois de ligar a variável, para os avisos irem para quem cuida da instância (a conferir no ensaio, seção 17), e olhar a aba uma vez por mês.

### 5.6 Cópia no armazenamento da empresa (opcional)

Com `CRM_BACKUP_REMOTE` e `CRM_BACKUP_RCLONE_CONFIG`, um passo a mais instala o `rclone` pelo `apt` (pacote do Ubuntu, sem script baixado por `curl | sh`), grava o `rclone.conf` em `$RUNNER_TEMP` com `umask 077` e roda `rclone copy <arquivo.7z> "$CRM_BACKUP_REMOTE"`. O mesmo arquivo cifrado vai para lá. O workflow **nunca apaga** no destino: a retenção é uma regra do armazenamento (ciclo de vida do bucket, ou a limpeza manual de uma pasta do Drive), que o guia manda configurar com o mesmo prazo da política da empresa. Opções sem custo para o tamanho do CRM: o Google Drive ou o OneDrive da empresa (conta da empresa, pasta restrita), Backblaze B2 ou Cloudflare R2 (camada gratuita; o guia não promete a cota e manda conferir). A cópia no armazenamento serve quem quer guardar mais do que o GitHub ou fora dele; a do GitHub continua.

### 5.7 LGPD: onde guardar, quem acessa e por quanto tempo

O backup tem todos os dados pessoais do CRM (contatos, anotações, e-mails e telefones da equipe, hashes de senha). O guia e [LGPD da instância](../LGPD-INSTANCIA.md) dizem, numa caixa só:

- **Onde:** o artefato do GitHub do repositório privado da empresa, e, se ligado, uma pasta do armazenamento da empresa com acesso restrito. Nunca no computador de alguém, num e-mail, num chat ou dentro da pasta do repositório (o `.gitignore` ganha `crm-backup-*`). Depois de restaurar, apague a pasta extraída e esvazie a lixeira.
- **Quem acessa:** quem tem leitura no repositório baixa o arquivo; só quem tem a senha o abre. A senha fica com o Dono, num gerenciador de senhas. Se quem implanta guarda as cópias, ele é operador e o termo registra (`<PLANO E RETENÇÃO DAS CÓPIAS>` na seção 10 da LGPD da instância).
- **Por quanto tempo:** 7 dias por padrão no GitHub, e o prazo definido pela empresa no armazenamento dela, que entra na política de retenção. Cópias mais longas guardam por mais tempo os dados de quem pediu anonimização.
- **Restaurar volta dados anonimizados.** A lista dos pedidos atendidos fica fora do CRM, com a data; depois de restaurar, refazer as anonimizações posteriores à data do backup (`createdAt`), que a ferramenta mostra no fim.
- **Troca da senha:** se alguém que conhecia a senha sair, gere outra e troque o secret; as cópias antigas expiram sozinhas no prazo.

## 6. Restauração

### 6.1 Caminho escolhido: migrações + dados, num projeto novo

1. Projeto Supabase **novo** (nunca por cima do projeto atual, que pode ter dados posteriores ao backup).
2. O repositório na mesma versão de migrações do backup e `npx supabase db push` no projeto novo: o schema completo, com extensões, schemas `auth` e `private`, gatilhos em `auth.users` e `auth.mfa_amr_claims`, permissões, RLS e o histórico de migrações, sai exatamente como num projeto implantado do zero.
3. `npm run backup:restore` grava só os dados.
4. `npm run config:push` (Auth, item 1.3), as variáveis da Vercel com a URL e a chave pública do projeto novo, e um deploy novo.

O caminho da documentação do Supabase (`roles.sql` + `schema.sql` + `data.sql` pelo `psql`) foi descartado como principal (seção 12): o `schema.sql` exclui o schema `auth` e perde os gatilhos do CRM nele (a própria documentação diz para restaurar à parte as mudanças em `auth`), as tabelas herdam os privilégios padrão do projeto novo (aviso da referência do CLI), exige `psql` e não deixa o histórico de migrações no lugar, o que quebraria o próximo `db push`.

**Versões diferentes.** A ferramenta exige o mesmo conjunto de versões em `supabase_migrations.schema_migrations` do projeto novo e no `history.sql`. Se o repositório está à frente (migrações novas depois do backup), o guia manda restaurar na versão do backup (`git switch --detach <commit do backup-info.json>`, `db push`, restaurar, `git switch -` e `db push` de novo, que aplica as migrações novas com os backfills sobre os dados restaurados, o caminho normal de atualização). Se o commit não bater (o banco tinha migrações que o commit não tem, ou o contrário), a ferramenta lista o que falta e o que sobra pelos nomes.

### 6.2 A ferramenta `backup:restore`

`scripts/restore-backup.mjs` (o processo) e `scripts/lib/backup-restore.mjs` (funções puras, no Vitest), com o `pg` já instalado e o leitor de SQL do runner (`splitSqlScript`, de `embedded-db.mjs`, com um modo restrito: nenhum meta-comando é seguido, nem `\ir`).

Uso, no PowerShell:

```powershell
$env:CRM_RESTORE_DB_URL = Read-Host 'Cole a conexão'
npm run backup:restore -- --dir "C:\Users\<você>\Documents\crm-restauracao" --confirm <ref do projeto novo>
npm run backup:restore -- --dir "C:\Users\<você>\Documents\crm-restauracao" --confirm <ref do projeto novo> --apply
Remove-Item Env:CRM_RESTORE_DB_URL
```

- A conexão vem só da variável de ambiente, lida pelo `Read-Host` (no macOS e no Linux, `read -rs CRM_RESTORE_DB_URL && export CRM_RESTORE_DB_URL`) para não ficar no histórico do terminal, que o PSReadLine e o bash ou zsh gravam em arquivo, e limpa no fim (rodada 2 da revisão, achado 4). `--confirm` precisa ser o *ref* que aparece na conexão (`postgres.<ref>` no usuário do pooler ou `db.<ref>.supabase.co`): evita restaurar no projeto errado.
- TLS: `pg` com verificação do certificado. Se a cadeia do Supabase não for aceita pelo Node, a mensagem manda baixar o certificado em Database → Settings → SSL Configuration e apontar `CRM_RESTORE_SSL_CA` para o arquivo; não há opção para desligar a verificação. (A confirmar no ensaio real, seção 17.)
- Saída em pt-BR, com as etapas, as contagens por tabela, o tempo e, no fim, o que falta fazer: `config:push`, Vercel, colar `supabase/db-drift-check.sql`, todos entram de novo e refazer as anonimizações depois de `createdAt`.

### 6.3 Etapas e recusas

1. **Pasta:** `data.sql`, `history.sql` e `backup-info.json` presentes; `sha256` de cada um igual ao do JSON; `format` conhecido. Senão: "Esta pasta não é um backup completo do CRM" com o arquivo.
2. **Dump:** cada comando de `data.sql`, depois de `splitSqlScript`, precisa ser um destes: `SET <nome> = <valor>`, `SELECT pg_catalog.set_config(...)`, `SELECT pg_catalog.setval(...)`, `INSERT INTO "<schema>"."<tabela>" (` com schema em `auth`, `public`, `private` ou `storage`, ou `RESET ALL`. Qualquer outro (DDL, `DO`, `COPY`, `INSERT` em outro schema) recusa com a linha. Uma linha `\restrict` sem comentário (um `pg_dump` cru, fora do CLI) recusa e explica que o backup deve vir do workflow ou do `supabase db dump`; outro meta-comando recusa. As versões vêm de `parseHistoryVersions(history.sql)`, um leitor das tuplas do `VALUES` que respeita aspas (a coluna `statements` guarda SQL de verdade).
3. **Projeto:** conecta, confere `--confirm`, lê as versões de `supabase_migrations.schema_migrations` e compara (seção 6.1).
4. **Transação:** `BEGIN`; `SET statement_timeout = 0`; roda `supabase/backup/restore-prepare.sql`: recusa uma sessão com `request.jwt.claims` (não é o editor nem uma conexão direta), conta as linhas de cada tabela de `public` e de `private` (pelo catálogo, então uma tabela nova da base entra sozinha) e de `auth.users`, e recusa se houver qualquer uma, listando as tabelas. A lista `RESTORE_SEEDED_TABLES`, de tabelas que uma migração preenche, está vazia hoje: nenhuma migração grava linha num projeto novo, e o `test:db` reprova o dia em que alguma passar a gravar sem a lista ser decidida.
5. **Carga:** cada comando de `data.sql`, na ordem. O `SET session_replication_role = replica` do próprio arquivo desliga os gatilhos e as conferências de chave estrangeira (que são gatilhos) só nesta sessão; o `RESET ALL` do fim religa. A ferramenta soma, por tabela, o número de linhas que cada `INSERT` informou (o `rowCount` do PostgreSQL), que vira a contagem esperada.
6. **Conferências** (seção 6.4), ainda na transação.
7. `--apply`: `COMMIT`; senão `ROLLBACK` e "Ensaio concluído: nada foi gravado. Rode de novo com --apply para restaurar.". Depois do `COMMIT`, a ferramenta roda a conferência de drift (`supabase/db-drift-check.sql`, uma consulta só, em `begin read only`) e mostra o resumo; uma diferença ali vem do schema (do `db push`), não dos dados, e o guia diz o que fazer.

Uma queda de rede, um `Ctrl+C` ou um erro do PostgreSQL em qualquer ponto antes do `COMMIT` desfaz tudo: o projeto continua vazio e a ferramenta pode rodar de novo.

### 6.4 Conferências antes de confirmar

- **Contagens:** para cada tabela que o dump preencheu, `count(*)` igual à soma do passo 5; as tabelas de `public` e `private` fora do dump continuam vazias.
- **Chaves estrangeiras:** `supabase/backup/restore-check.sql` monta, pelo catálogo, uma consulta "órfãos" para cada FK de `public` e `private` (inclusive as que apontam para `auth.users`), com a regra `MATCH SIMPLE` (qualquer coluna nula pula a linha), e recusa listando a restrição e quantas linhas. É a garantia que o modo `replica` tirou da carga; pega um dump parcial (uma tabela excluída por `-x`).
- **Gatilhos e RLS:** nenhum gatilho de usuário desligado (`tgenabled = 'D'`) em `public`, `private`, `auth.users` e `auth.mfa_amr_claims`; toda tabela de `public` com RLS ligada. Os dois vêm das migrações; a conferência protege contra um projeto preparado à mão.
- `CHECK`, `NOT NULL` e `UNIQUE` não dependem de gatilho e valem durante a carga.

### 6.5 Alternativa com `psql` (Linux, macOS ou quem já tem)

O guia mostra, como alternativa, a mesma ordem pelo `psql`, com os mesmos arquivos de apoio: `psql --single-transaction -v ON_ERROR_STOP=1 -f supabase/backup/restore-prepare.sql -f data.sql -f supabase/backup/restore-check.sql "$CRM_RESTORE_DB_URL"`. Sem a comparação das versões e das contagens, que só a ferramenta faz; serve também para um banco grande demais para a ferramenta (que lê o arquivo inteiro na memória: até algumas centenas de MB).

## 7. O ensaio automatizado (`npm run test:restore`)

### 7.1 Onde roda

- `scripts/test-restore.mjs`, com o prefixo temporário `crm-restore-` em `TEMP_PREFIXES`. Comando manual documentado no README e job novo do CI.
- **Exige `pg_dump` 17 ou mais novo** (a versão precisa ser pelo menos a do servidor). Procura em `CRM_PG_BIN`, no PATH e, no Windows, em `C:\Program Files\PostgreSQL\<17 a 19>\bin`. Sem ele, termina com 1 e diz como obter: no Windows, o instalador oficial com só "Command Line Tools", ou os binários em zip, sem instalar, apontados por `CRM_PG_BIN`; no macOS, `brew install libpq`; no Linux, `postgresql-client-17` do PGDG. O ensaio não passa a ser "pulado": quem roda o comando quer a prova.
- **CI:** job `restauracao` em `ci.yml`, com os mesmos gatilhos do `e2e` (pull request para `main`, toda noite e `workflow_dispatch`), `timeout-minutes: 20`: `npm ci`, `sudo apt-get install -y postgresql-client-17` (com o repositório do PGDG pelo `apt.postgresql.org.sh` de `postgresql-common` se o pacote não estiver disponível) e `npm run test:restore -- --check-cli`. Fora do `qualidade` porque precisa de rede, do cliente 17 e de minutos; estimado em 3 a 5 minutos por execução.
- **Nesta máquina** não há `pg_dump`. A implementação precisa de um: com a autorização do dono para o download, os binários oficiais do PostgreSQL 17 para Windows (zip da EDB, link em postgresql.org/download/windows) extraídos na pasta temporária da sessão, sem instalar nada no sistema, com `CRM_PG_BIN`; sem a autorização, a primeira execução real fica para o job do CI depois do push do `@devops`, e o coordenador decide se o item pode ser marcado antes disso (seção 17).

### 7.2 Fluxo

O cluster descartável ganha dois recursos em `embedded-db.mjs`: `database` em `withSession`, `runInFreshSession`, `openSession` e `applySchema` (hoje tudo vai para `postgres`), e `applySchema({ recordHistory: true })`, que cria `supabase_migrations.schema_migrations(version text primary key, statements text[], name text)` e grava cada migração aplicada, como o CLI. O bootstrap local passa a criar os papéis com a guarda de `duplicate_object` (papéis são do cluster; o schema `auth` e os privilégios padrão são de cada banco).

1. Banco `crm_origem`: bootstrap, todas as migrações (as da base e as `_custom_` presentes, como o `db push`), histórico.
2. Dados: o Dono, uma administradora, um colaborador e uma pessoa desativada em `auth.users` com `encrypted_password`, a empresa por `private.provision_organization`, os papéis, uma sessão com `mfa_amr_claims` (e a prova de e-mail que o gatilho grava), um convite pendente e o seed de demonstração (`supabase/seed-demo.sql`, com a anonimização, os itens, as automações e os recebimentos). Reaproveita os auxiliares do `test:db` extraídos para `scripts/lib/demo-instance.mjs`, sem duplicar.
3. Dump: `pg_dump` com `CLI_DATA_DUMP` (seção 5.4) mais os `-x` do workflow, o mesmo pós-processamento do CLI, em `data.sql`; o mesmo para o histórico; `backup-info.json` com os `sha256`.
4. Banco `crm_destino`: bootstrap, as mesmas migrações e o histórico. `backup:restore` (as funções de `backup-restore.mjs`, não um processo à parte) com `--apply`.
5. Conferências (7.3).
6. Recusas (7.4), cada uma num banco de destino novo ou em transação desfeita.

### 7.3 Conferências do ensaio

- **Conteúdo, não só contagem:** para cada tabela de `public`, `private` e `auth` que existe nos dois bancos, a contagem e um `md5` das linhas ordenadas (`string_agg(t::text, '|' order by t::text)`) iguais na origem e no destino; as cinco tabelas excluídas vazias no destino.
- **Senhas e identidades:** `auth.users.encrypted_password` igual; a pessoa desativada continua desativada.
- **RLS:** como o colaborador (claims), as mesmas linhas de `contacts`, `deals` e `activities` na origem e no destino; como a pessoa desativada, nenhuma (1.2); como `anon`, nenhuma; `privacy_actions` sem escrita para a API (1.10).
- **Gatilhos funcionando depois da carga:** uma edição de contato pelo colaborador grava a auditoria e o `updated_at`; um cadastro sem convite em `auth.users` é recusado (`enforce_invite_only_signup`, 1.1); uma sessão nova com `mfa_amr_claims` grava a prova (`record_email_proof`); uma ação de contato agendada para quem está "Não contatar" é recusada (1.10).
- **Extensões e schemas:** o mesmo conjunto de `pg_extension` (nome e schema) e de schemas nos dois bancos; `private` com o mesmo dono e ACL; as funções de `private` com `search_path` vazio.
- **Drift zero:** `private.base_fingerprints()` do destino igual à da origem e ao `supabase/base-manifest.json` (só a base).
- **Funcional:** `supabase/seed-demo-remove.sql` roda no destino e apaga a demonstração (os vínculos e os ids sobreviveram).
- **O caminho descartado, provado:** num terceiro banco, bootstrap + o `pg_dump` de schema com as opções do CLI (sem `auth`) + os dados: os gatilhos do CRM em `auth.users` e `auth.mfa_amr_claims` não existem. A asserção documenta o motivo da decisão B8 e impede que alguém "simplifique" o guia para o caminho da documentação. Se esse caminho exigir ajustes demais no cluster local (privilégios ou extensões que só o Supabase tem), a implementação registra o motivo na seção de ajustes e mantém a asserção mínima: o `schema.sql` gerado não contém `CREATE TRIGGER` em `"auth"`.

### 7.4 Recusas do ensaio

Destino com uma linha em `public.contacts`; destino com uma conta; destino sem a última migração no histórico (a mensagem cita o nome); `--confirm` errado; `sha256` alterado; um `DROP TABLE` acrescentado ao `data.sql`; um `\ir` e um `\restrict` sem comentário; um dump sem `public.companies` (`-x`): a conferência de chaves estrangeiras recusa, e o destino continua vazio. Sem `--apply`: tudo gravado e conferido, e o destino vazio no fim.

## 9. Fluxos

O item não tem tela nova no CRM. Os fluxos são de quem administra:

- **Ligar o backup:** criar a senha do arquivo no gerenciador de senhas → Settings → Secrets and variables → Actions: os dois secrets e a variável `CRM_BACKUP_ENABLED = true` → Actions → "Backup do banco" → desativar e reativar → "Run workflow" → conferir o artefato e abri-lo uma vez com o 7-Zip.
- **Restaurar:** projeto novo → baixar o artefato (ou pegar no armazenamento) → extrair fora da pasta do repositório → versão das migrações → `link` + `db push` → ensaio sem `--apply` → `--apply` → `config:push` → Vercel → entrar com uma conta → drift → refazer as anonimizações → apagar a pasta extraída.
- **Ensaio periódico:** o guia recomenda restaurar a cada três meses num projeto Free temporário (e excluí-lo depois), para saber que a senha e o caminho funcionam.

## 10. Casos de borda e corrida

| Caso | Comportamento |
| --- | --- |
| Equipe gravando durante o dump | O `pg_dump` de dados usa uma fotografia só; as tabelas ficam coerentes entre si. |
| Migração aplicada durante o backup | O histórico lido antes e depois difere e o job falha (seção 5.3). |
| Duas execuções do workflow | `concurrency` sem cancelamento: a segunda espera. |
| Projeto Free pausado | O dump falha por conexão; o aviso de falha vai por e-mail (seção 5.5). O guia diz que um projeto pausado não tem backup. |
| Senha do banco com `@`, `#`, `/`, `%` | O CLI exige a URL codificada; o guia traz a tabela dos caracteres e o job recusa uma URL que o `URL` do Node não lê. |
| Limite de download de imagem do Docker no runner | O passo do dump repete uma vez; continuando, falha com a mensagem de rodar de novo mais tarde. |
| Restaurar duas vezes | A segunda recusa: o projeto já tem dados. |
| Restaurar no projeto atual por engano | `--confirm` + projeto vazio: o projeto em uso nunca está vazio. |
| Queda no meio da restauração | Transação desfeita; projeto continua vazio. |
| Projeto novo com conta criada antes de restaurar | Recusa (conta em `auth.users`); o guia manda restaurar antes do primeiro acesso. |
| Auth do projeto novo com colunas a mais | Os `INSERT` levam a lista de colunas; colunas novas ficam com o padrão. |
| Tabela de `auth` já preenchida pelo Supabase no projeto novo | O `INSERT` falha por chave repetida; a transação é desfeita e a mensagem cita a tabela (a confirmar no ensaio real). |
| Migrações `_custom_` do aluno | Estão no repositório e no histórico; o `db push` as aplica e o dump traz os dados das tabelas `custom_`. |
| Dados de quem pediu anonimização depois do backup | A restauração os traz de volta; a ferramenta mostra a data e o guia manda refazer pela lista fora do CRM. |
| Banco muito grande | A ferramenta lê o arquivo inteiro; acima de algumas centenas de MB, o guia indica o `psql` (seção 6.5). |
| Repositório tornado público depois | O próximo job recusa; os artefatos antigos continuam baixáveis até expirar: o guia manda excluí-los na aba Actions. |

## 11. Caminho de atualização para instâncias existentes

Nada a aplicar no banco. Uma instância que atualizar a base recebe o workflow desligado (nenhum efeito até ligar a variável), os scripts e os guias. O dono do produto não precisa aplicar migração por este item; a lista de migrações pendentes do [ambiente do dono](../dono/AMBIENTE.md) não muda.

## 12. Alternativas consideradas

- **Restaurar pelo `schema.sql` do CLI (caminho da documentação):** perde os gatilhos em `auth`, herda os privilégios padrão, exige `psql` e deixa o histórico vazio. Descartada como principal (B8), com a prova no ensaio (7.3).
- **`--use-copy` no dump:** mais rápido, mas `COPY ... FROM stdin` exige `psql` (o `pg` não executa sem outra biblioteca). Para o tamanho do CRM, `INSERT` basta (B4).
- **Workflow fora de `.github/workflows/`, para copiar, ou com o `schedule` comentado:** ligar exigiria editar ou copiar um arquivo da base e perderia as correções das atualizações (5.1).
- **Artefato sem cifra, protegido só pelo repositório privado:** qualquer colaborador com leitura baixaria todos os dados pessoais. Descartada.
- **`gpg --symmetric` ou um formato próprio cifrado pelo Node:** o `gpg` não vem no Windows (só dentro do Git, pouco acessível para quem não é desenvolvedor); um formato próprio deixaria o backup ilegível sem o repositório. O `.7z` com AES-256 abre no 7-Zip, gratuito e conhecido.
- **`GitHub Environments` com aprovação:** em repositório privado, exigem plano pago do GitHub.
- **Workflow de restauração no GitHub Actions:** evitaria até o Node local, mas guardaria no GitHub a credencial de escrita de um projeto e tornaria a gravação de todos os dados um botão. A restauração é rara e acompanhada: fica local.
- **Apagar as tabelas do projeto novo antes de carregar:** a ferramenta nunca apaga (B10); hoje um projeto recém-migrado está vazio.
- **Ensaio com um "dumper" em Node no lugar do `pg_dump`:** não seria um dump de verdade e envelheceria. Descartada; o ensaio exige o `pg_dump` 17.

- **PITR ou cópia física:** pagos ou do Supabase; fora da premissa 4.
