## 1. Objetivo

A empresa que vende produtos ou serviços de preço conhecido monta hoje o valor da oportunidade de cabeça: soma no papel, digita o total e perde o detalhe do que foi negociado. Quem vende serviço recorrente (o caso típico dos alunos: gestão de tráfego, consultoria mensal, assinatura) não tem como registrar "R$ 2.000,00 por mês durante 12 meses mais R$ 1.500,00 de implantação", e a previsão mistura mensalidade com venda única. O item entrega:

1. um catálogo simples, mantido por donos e administradores, consultado por todos;
2. itens na oportunidade, do catálogo ou avulsos, com quantidade, unidade, preço negociado, desconto por item e cobrança única ou mensal;
3. o valor da oportunidade calculado pelos itens (total único, mensalidade e valor do contrato), sem diferença de um centavo entre a tela e o banco;
4. os números de Pipeline, previsão e Relatórios usando um valor definido e explicado;
5. a importação do catálogo por planilha e a exportação dos itens;
6. a base de dados que o financeiro ampliado (2B.14) e as propostas (2B.15) vão usar.

## 3. Critérios de aceite

1. **AC-1 Catálogo:** em "Configurações" › "Catálogo", donos e administradores criam, editam, arquivam, reativam e excluem itens do catálogo (nome, código, tipo, unidade, preço, cobrança); colaboradores e "Somente leitura" veem a lista e o aviso "Somente donos e administradores alteram o catálogo. Você pode consultá-lo.", sem os botões. O banco recusa a escrita de quem não é dono ou administrador e a leitura de outra organização (`test:db`).
2. **AC-2 Código único:** dois itens com o mesmo código na organização são recusados, sem diferença de maiúscula e espaços nas pontas, com "Já existe um item com o código “X”." na tela.
3. **AC-3 Arquivar e excluir:** item arquivado some do seletor do editor de itens (inclusive na importação de planilha, que não o reativa) e continua nos itens que já o usam, com "(arquivado)"; excluir um item já usado em oportunidade é recusado pelo banco (23503) com "Este item já foi usado em oportunidades. Arquive para tirá-lo das escolhas."
4. **AC-4 Itens:** quem edita oportunidades (dono, administrador, colaborador) adiciona, altera e remove itens no formulário ("Nova oportunidade" e "Editar") e no painel ("Editar itens"), do catálogo (busca por nome ou código) ou avulsos, no desktop e no celular, sem rolagem lateral a 320 px. "Somente leitura" vê os itens e os totais, sem editar.

## 4. Modelo de dados e RPC

Migração `supabase/migrations/20261019100000_product_catalog.sql`, nova, aditiva e segura para instâncias com dados. Comentários em português, no estilo das migrações do 1.2 e do 1.10 (o que muda, por quê e o que não muda).

### 4.1 `public.products`

```sql
create table public.products(
 id uuid primary key default gen_random_uuid(),
 org_id uuid not null references public.organizations(id),
 name text not null,
 code text,
 kind text not null default 'product',
 unit text,
 price numeric(16,2) not null,
 billing text not null default 'one_time',
 archived_at timestamptz,
 created_at timestamptz not null default now(),
 updated_at timestamptz not null default now(),
 unique(id,org_id),
 constraint products_name_length check(length(btrim(name)) between 1 and 160),
 constraint products_code_length check(code is null or length(btrim(code)) between 1 and 40),
 constraint products_kind check(kind in ('product','service')),
 constraint products_unit_length check(unit is null or length(btrim(unit)) between 1 and 20),
 constraint products_price_valid check(price>=0 and price<>'NaN'::numeric and price<=999999999999.99),
 constraint products_billing check(billing in ('one_time','monthly')),
 constraint products_archived_at_finite check(isfinite(archived_at)),
 constraint products_created_at_finite check(isfinite(created_at)),
 constraint products_updated_at_finite check(isfinite(updated_at))
);
create unique index products_org_code on public.products(org_id,lower(btrim(code))) where code is not null;
create index products_org_name on public.products(org_id,name);
```

- **Tipo padrão `product`** (o formulário começa em "Produto"; a importação usa "Produto" para a célula vazia) e **cobrança padrão `one_time`**. São padrões de tela, sem efeito no cálculo.
- **`archived_at`** em vez de um booleano: guarda quando o item saiu das escolhas. Nulo = ativo.
- **Nome não é único** (o mesmo serviço pode existir com unidades diferentes); o código, quando informado, é. A importação trata nome igual sem código como repetida (seção 8.3), para a mesma planilha não duplicar o catálogo.
- **RLS e grants** (padrão das configurações desde `20260906051832_configuration_policies_by_operation.sql`): `revoke all ... from public,anon,authenticated`; `grant select,insert,update,delete ... to authenticated`; `tenant_read` (organização), `tenant_insert`, `tenant_update` e `tenant_delete` com `org_id=(select private.current_org()) and (select private.can_manage())`. `current_org()` exige papel ativo (1.2): quem foi desativado não lê nem grava.
- **Gatilhos:** `protect_record_metadata` (antes de inserir e atualizar), `touch_updated_at` (antes de atualizar) e `audit_record_change` (depois de inserir, atualizar e excluir), as mesmas funções das demais tabelas.

### 4.2 `public.deal_items`

```sql
create table public.deal_items(
 id uuid primary key,
 org_id uuid not null references public.organizations(id),
 deal_id uuid not null,
 product_id uuid,
 position integer not null,
 name text not null,
 quantity numeric(12,3) not null,
 unit text,
 unit_price numeric(16,2) not null,
 discount_type text,
 discount_value numeric(16,2) not null default 0,
 billing text not null,
 line_total numeric(16,2) generated always as (
  round(quantity*unit_price,2)
  - case discount_type when 'percent' then round(round(quantity*unit_price,2)*discount_value/100,2)
                       when 'amount' then discount_value else 0 end
 ) stored,
 created_at timestamptz not null default now(),
 updated_at timestamptz not null default now(),
 unique(id,org_id),
 constraint deal_items_deal_id_org_id_fkey foreign key(deal_id,org_id) references public.deals(id,org_id) on delete cascade,
 constraint deal_items_product_id_org_id_fkey foreign key(product_id,org_id) references public.products(id,org_id),
 constraint deal_items_position check(position between 0 and 99),
 constraint deal_items_name_length check(length(btrim(name)) between 1 and 160),
 constraint deal_items_quantity check(quantity>0 and quantity<>'NaN'::numeric),
 constraint deal_items_unit_length check(unit is null or length(btrim(unit)) between 1 and 20),
 constraint deal_items_unit_price check(unit_price>=0 and unit_price<>'NaN'::numeric),
 constraint deal_items_gross_limit check(round(quantity*unit_price,2)<=999999999999.99),
 constraint deal_items_discount check(
  (discount_type is null and discount_value=0)
  or (discount_type='percent' and discount_value>0 and discount_value<=100)
  or (discount_type='amount' and discount_value>0 and discount_value<=round(quantity*unit_price,2))),
 constraint deal_items_billing check(billing in ('one_time','monthly')),
 constraint deal_items_created_at_finite check(isfinite(created_at)),
 constraint deal_items_updated_at_finite check(isfinite(updated_at))
);
create index deal_items_deal_position on public.deal_items(org_id,deal_id,position);
create index deal_items_deal_id_org_id_fkey_idx on public.deal_items(deal_id,org_id);
create index deal_items_product_id_org_id_fkey_idx on public.deal_items(product_id,org_id);
```

- **Nome, unidade, preço e cobrança gravados no item** (cópia do catálogo no momento da escolha, editável): mudar o preço ou o nome no catálogo não muda negociações já feitas, e a proposta (2B.15) mostra o que foi negociado. O item avulso tem `product_id` nulo.
- **`id` sem padrão:** vem do navegador (`crypto.randomUUID()`), para a gravação por diferença e a repetição segura (seção 4.5).
- **Desconto com uma representação só:** sem desconto, `discount_type` nulo e valor 0; percentual entre 0 e 100 (excluído o 0, com até 2 casas); em reais, até o bruto da linha. A RPC normaliza "desconto 0" para nulo antes de gravar.
- **`ON DELETE CASCADE` na oportunidade:** os itens são parte dela. `delete_deal` (0.7) não muda: os itens saem com a oportunidade, e o diálogo de exclusão passa a dizer "Os itens da oportunidade são excluídos com ela." Na FK do produto, sem `ON DELETE`: excluir item do catálogo já usado é recusado (AC-3).
- **RLS e grants:** `revoke all ... from public,anon,authenticated`; `grant select ... to authenticated`; só `tenant_read`. Nenhum papel da API insere, altera ou exclui: a RPC é a única escritora, como `deal_stage_history` e `privacy_actions` são escritos só pelo banco.
- **Gatilhos:** `protect_record_metadata`, `touch_updated_at` e `audit_record_change`, como em `products`.

### 4.3 O cálculo, num lugar só no banco

O total da linha é a coluna gerada: nenhum caminho (RPC, SQL de manutenção, futura importação de oportunidades) grava um total diferente do que quantidade, preço e desconto dizem. As regras:

1. **bruto** = `round(quantidade × preço unitário, 2)`;
2. **desconto** = em %: `round(bruto × percentual / 100, 2)`; em R$: o valor; sem desconto: 0;
3. **total da linha** = bruto − desconto (≥ 0 pelo `CHECK` do desconto);
4. **total único** = soma dos totais das linhas com cobrança única; **mensalidade** = soma das linhas mensais;
5. **valor do contrato** = total único + mensalidade × meses do contrato.

Todo arredondamento é em centavos, metade para cima (valores nunca negativos), feito uma vez por linha: o desconto em % arredonda sobre o bruto já arredondado, e os totais somam linhas já arredondadas, sem novo arredondamento. Assim a soma das linhas exibidas é sempre o total exibido.

### 4.4 Colunas novas em `public.deals`

```sql
alter table public.deals add column item_count integer not null default 0;
alter table public.deals add column one_time_value numeric(16,2);
alter table public.deals add column monthly_value numeric(16,2);
alter table public.deals add column contract_months integer;
alter table public.deals add constraint deals_item_count check(item_count between 0 and 100);
alter table public.deals add constraint deals_item_totals check(
 (item_count=0 and one_time_value is null and monthly_value is null and contract_months is null)
 or (item_count>0 and one_time_value>=0 and monthly_value>=0
     and (contract_months is null or contract_months between 1 and 120)));
alter table public.deals add constraint deals_value_from_items check(
 item_count=0 or value=one_time_value+monthly_value*coalesce(contract_months,0));
```

- **`value` continua a coluna lida por todos** e passa a ser o valor do contrato quando há itens (C3, C4). `numeric(16,2)` e os `CHECK` de hoje (`value>=0`, `deal_value_finite`) valem.
- **`deals_value_from_items`** recusa (23514) qualquer mudança de `value` numa oportunidade com itens que não venha junto das partes, inclusive de um frontend antigo. A tela reconhece o nome da restrição na mensagem do PostgREST e mostra "O valor desta oportunidade vem dos itens. Para mudar o valor, edite os itens." (`errorMessage`, em `src/components/pipeline/data.ts`).
- **Meses obrigatórios com item mensal** (C7) é regra da RPC (o `CHECK` não enxerga os itens); o `test:db` confere que toda oportunidade com item mensal tem meses.
- **Gatilho `protect_deal_totals`** (`BEFORE INSERT OR UPDATE`, `SECURITY INVOKER`, sem ler outra tabela): fora da gravação dos itens (marca `crm.saving_deal_items` igual ao id da linha, ligada só na transação pela RPC, como `crm.anonymizing_contact` no 1.10), na inserção zera `item_count` e anula as três partes, e na atualização devolve os valores antigos das quatro colunas. Com o `CHECK`, um cliente não desliga os itens nem troca o valor: só a RPC muda as partes. Em ordem alfabética, roda depois de `guard_anonymized_contact` e antes de `protect_record_metadata`, `refuse_inactive_assignee`, `touch_updated_at` e `validate_deal_change`, que não leem essas colunas.
- **A marca só na transação** (`set_config('crm.saving_deal_items', id, true)`), desligada ao fim da gravação, pelo mesmo motivo do `crm.bulk_move` do 0.7: ligada na sessão, ficaria na conexão compartilhada do PostgREST.

### 4.5 `public.save_deal` e `private.save_deal`

```sql
public.save_deal(
 p_deal_id uuid,               -- id da oportunidade; na criação, gerado no navegador
 p_version timestamptz,        -- updated_at lido; nulo = criar
 p_fields jsonb default null,  -- campos do formulário; nulo = não mexe nos campos
 p_items jsonb default null,   -- lista completa de itens; nulo = não mexe nos itens; [] = remove todos
 p_contract_months integer default null  -- considerado só com p_items
) returns jsonb               -- {"deal": <linha de deals>, "items": [<linhas de deal_items>], "replayed": bool}
language sql security invoker set search_path='' as $$ select private.save_deal(...) $$;
```

`private.save_deal` é `SECURITY DEFINER` com `search_path=''` (precisa escrever em `deal_items`, que a API não escreve). Como passa por cima da RLS, confere tudo o que a política conferiria e mais:

1. **Quem:** `auth.uid()` e `private.current_org()` presentes e `private.can_write()`; senão, "Você não tem permissão para alterar oportunidades." com `errcode='insufficient_privilege'` (a tela já traduz 42501).
2. **Nada a fazer** (`p_fields` e `p_items` nulos): recusa.
3. **Criar** (`p_version` nulo): se já existe uma oportunidade com `p_deal_id` na organização, devolve-a com os itens e `"replayed": true`, sem mudar nada (a repetição depois de uma resposta perdida, como `complete_activity`); em outra organização, "Oportunidade indisponível ou sem acesso.". Senão insere com `org_id = current_org()` e os campos permitidos na criação (`title`, `pipeline_id`, `stage_id`, `status`, `currency`, `value`, `owner_id`, `contact_id`, `company_id`, `close_date`, `probability`, `lost_reason`). Com itens, o valor inserido é 0 e a atualização do passo 6 grava o do contrato.
4. **Editar** (`p_version` informado): `select ... for update` da oportunidade `where id=p_deal_id and org_id=current_org()`; sem linha ou com `updated_at is distinct from p_version`: "Esta oportunidade mudou ou não está mais disponível. Seus dados continuam no formulário; feche, confira a versão atual e edite de novo." Campos permitidos na edição: `title`, `value`, `owner_id`, `contact_id`, `company_id`, `close_date`, `probability`, `lost_reason` e `closed_at` (só quando a chave vem, como o formulário de hoje). Etapa e situação continuam só por `move_deal`. Uma chave fora da lista é recusada ("Campo desconhecido: …"), para um erro do cliente não passar calado.
5. **Itens** (`p_items` não nulo): valida a lista inteira antes de gravar e recusa com a posição e o nome do item ("Item 2 (Consultoria): …"):
   - array com no máximo 100 objetos e ids distintos; um id que já existe em outra oportunidade é recusado ("Este item não pertence a esta oportunidade.");
   - `name` aparado, de 1 a 160 caracteres; `unit` aparada, até 20, vazia vira nula;
   - `quantity`, `unit_price` e `discount_value` chegam como texto decimal (`"1.500"`, `"1500.00"`), nunca como número do JSON: a RPC lê `->>` como `numeric` e confere `scale()` (até 3 casas na quantidade e 2 nos valores) antes de gravar, para o `numeric(16,2)` não arredondar em silêncio; quantidade > 0 e até 999.999.999,999; preço de 0 a 999.999.999.999,99; bruto da linha até 999.999.999.999,99;
   - desconto: tipo `percent`, `amount` ou nulo, com as regras do `CHECK`, e "desconto 0" vira sem desconto;
   - `billing` `one_time` ou `monthly`;
   - `product_id`: do catálogo da organização; num item novo ou que trocou de produto, o produto precisa estar ativo ("“X” foi arquivado no catálogo. Escolha outro item ou use um item avulso."); o item que já tinha o produto arquivado continua.
   
   Depois grava por diferença: exclui os itens da oportunidade que não vieram, atualiza os que vieram com id existente (só quando algo mudou, para a auditoria não ganhar linhas vazias) e insere os novos, com `position` = índice na lista. Lê de volta a contagem, o total único e a mensalidade (somas de `line_total`); com item mensal, exige `p_contract_months` entre 1 e 120 ("Informe por quantos meses o contrato vale, de 1 a 120."); sem item mensal, os meses ficam nulos. Valor do contrato acima de 999.999.999.999,99 é recusado ("O valor do contrato passa do limite de R$ 999.999.999.999,99. Revise as quantidades e os preços.").
6. **Uma atualização da oportunidade** (com a marca ligada): os campos do passo 4 e, com itens gravados, `item_count`, `one_time_value`, `monthly_value`, `contract_months` e `value` = valor do contrato. Sem itens depois da gravação (`[]`), as partes ficam nulas e `value` é o de `p_fields.value`, se veio, ou o valor que já estava (o último valor calculado, AC-7). Com itens e um `p_fields.value` diferente do valor do contrato: "O valor desta oportunidade vem dos itens. Para mudar o valor, edite os itens." Na edição, uma atualização só (uma linha de auditoria); na criação com itens, a inserção e uma atualização.
7. Desliga a marca e devolve a oportunidade e os itens em ordem.

**Gatilhos que passam:** `validate_deal_change` (situação e etapa não mudam na edição; `closed_at` só com a chave), `refuse_inactive_assignee` (mudar itens de uma oportunidade com responsável desativado passa, porque não é trabalho novo; trocar para um desativado continua recusado), `guard_anonymized_contact` (o contato não muda), `record_deal_change` e `run_deal_automations` (não disparam: etapa e situação não mudam; na criação, `deal_created` dispara uma vez, como hoje), `touch_updated_at` (a versão nova volta na resposta) e `audit_record_change` (uma linha por item criado, alterado ou excluído e uma pela oportunidade).

**Travas:** a oportunidade em `FOR UPDATE` antes de tocar os itens; duas gravações da mesma oportunidade se enfileiram, e a segunda relê a versão nova (READ COMMITTED) e é recusada. A ordem é a mesma de `delete_deal` e de `anonymize_contact` (oportunidade, depois o que depende dela): sem espera circular. A desativação do 1.2 trava as oportunidades em `FOR NO KEY UPDATE`, que conflita com o `FOR UPDATE`: uma espera a outra, e a gravação que vier depois encontra a versão nova e mostra o conflito. Produto: a FK toma `FOR KEY SHARE`, que não espera quem arquiva (`FOR NO KEY UPDATE`).

**Execução:** `revoke execute ... from public,anon` nas duas; `grant execute ... to authenticated` nas duas (o padrão da base: a pública chama a privada como quem pediu); `revoke execute` de `private.protect_deal_totals()` de `public,anon,authenticated,service_role`.

### 4.6 Privacidade (funções do 1.10 substituídas, mesmas assinaturas)

O roteiro (regra do 1.10, no 1.8) pede que todo campo novo de texto livre com dado pessoal entre na anonimização e na exportação. O nome do item avulso é texto livre ("Consultoria para Ana Souza"). ## 5. Cálculo na tela

### 5.1 Módulo puro `src/lib/deal-item-math.ts`

Sem importação nenhuma (nem `@/`), para a fixture do E2E importá-lo por caminho relativo e emular a RPC com a mesma conta. Trabalha com inteiros:

- quantidade em milésimos (`bigint`), preço e valores em centavos (`bigint`), percentual em centésimos de ponto;
- `lineAmounts({ quantityMilli, unitPriceCents, discount })` → `{ grossCents, discountCents, totalCents }`, com `gross = (q × p + 500n) / 1000n` e desconto % `= (gross × pct + 5000n) / 10000n` (metade para cima, como o `round` do PostgreSQL para valores não negativos);
- `dealItemTotals(lines, months)` → `{ oneTimeCents, monthlyCents, contractCents }`;
- `decimalText(units, scale)` → `"1500.00"` / `"1.500"`, o texto que vai para a RPC;
- os limites (bruto e contrato até 99.999.999.999.999 centavos, quantidade até 999.999.999.999 milésimos) como constantes exportadas.

O resultado volta para a tela como `number` em centavos só depois de conferido o limite (abaixo de `Number.MAX_SAFE_INTEGER`).

### 5.2 `src/lib/deal-logic.ts`

O pedido do roteiro ("cálculo em `deal-logic`"): as funções de tela ficam aqui, sobre o módulo puro, e são testadas em `deal-logic.test.ts`.

- `parseQuantity(texto)`: padrão brasileiro como `parseBRL` (D7): com vírgula, a vírgula é decimal (até 3 casas: "0,125") e os pontos são milhar; sem vírgula, "1.500" é milhar e um único ponto com 1 ou 2 casas é decimal ("1.5" = 1,5); recusa vazio, zero, negativo, notação científica e mais de 3 casas.
- `parseDiscountPercent(texto)`: "10", "12,5" ou "12,50"; maior que 0 e até 100, até 2 casas.
- `dealItemDraft(item?, product?)`, `computeDealItems(drafts, months)` (com os erros por campo, nas mesmas palavras da RPC), `dealItemsPayload(drafts)` (ids, textos decimais e posição), `contractMonthsError(drafts, months)`.
- `dealValueBreakdown(deal)`: "R$ 1.500,00 único + R$ 2.000,00/mês × 12 meses", ou só uma das partes; `hasDealItems(deal)` (`item_count > 0`, ausente = falso).
- `validateDealDraft` deixa de exigir o valor quando o rascunho tem itens.

### 5.3 Paridade com o banco

`src/lib/deal-item-cases.json` lista casos com a entrada (quantidade, preço, desconto, cobrança, meses) e o esperado em centavos: arredondamento na metade (0,005), quantidade fracionada (1,333 × 0,03), desconto de 100%, desconto em R$ igual ao bruto, preço zero, mensalidade com 1 e com 120 meses, os limites e, como recusas, desconto em R$ acima do bruto, 4 casas na quantidade e 3 no preço. `deal-logic.test.ts` confere a tela contra o esperado; o runner do `test:db` (`scripts/test-database.mjs`, verificação `dealItemParity`, com PASS contados) lê o mesmo arquivo, grava cada caso por `private.save_deal` numa transação desfeita e confere `line_total`, `one_time_value`, `monthly_value` e `value`. Os dois lados batem com o mesmo esperado, logo batem entre si.

### 5.4 Meses do contrato

O campo "Meses do contrato" aparece no bloco de totais quando há ao menos um item mensal, começa vazio e é obrigatório ("Informe por quantos meses o contrato vale, de 1 a 120."). Sem sugestão de 12: o número muda a previsão, e quem vende precisa dizer o que negociou. Ao remover o último item mensal, o campo some e os meses vão vazios.

## 6. Qual valor conta onde

### 6.1 A regra

| Lugar | Valor | Motivo |
| --- | --- | --- |
| `deals.value` (com itens) | Valor do contrato = total único + mensalidade × meses | É o que a negociação vale, como o "valor total do contrato" dos CRMs de mercado; mantém todos os consumidores de hoje sem trocar de coluna. |
| Totais do Pipeline e das etapas, "Previsão ponderada" (Pipeline e Relatórios) | Valor do contrato (× probabilidade, na previsão) | A previsão estima o que a carteira vale; com contrato de 12 meses, o contrato inteiro entra ponderado. |
| Relatórios: aberto, ganho, perdido, "Valor aberto por funil" | Valor do contrato | O mesmo número do Pipeline, pela data de fechamento (0.6). |
| "Ganhos por responsável" (1.14) | Valor do contrato, com "inclui R$ X/mês × os meses" quando há mensalidade | Mesmo número dos ganhos; a mensalidade orienta quem acompanha recorrência. |
| "Mensalidades ganhas" (novo, Relatórios) | Soma de `monthly_value` das ganhas no período | Recorrência ganha por mês; o valor ganho já a soma vezes os meses de cada contrato; aparece só quando alguma ganha do recorte tem mensalidade. |
| Painel da oportunidade | Valor do contrato em destaque e, abaixo, o detalhamento | O detalhamento explica o número. |
| Cartão do quadro, ficha 360, Copiloto | Valor do contrato | Sem mudança de tela. |
| Planilha das oportunidades | "Valor BRL" = valor do contrato, mais "Total único BRL", "Mensalidade BRL" e "Meses do contrato" | Quem leva para a planilha recalcula como quiser. |
| Exportação do titular (LGPD) | Valor do contrato, as partes e os itens | Seção 4.6. |
| Financeiro | Não muda | O valor da oportunidade continua não sendo dinheiro recebido; parcelas e recorrência ficam com o 2B.14. |

### 6.2 Mudanças nos módulos

- `summarizeReport` (`operation-logic.ts`) ganha `wonMonthly` (centavos de `monthly_value` das ganhas no período); `summarizeDeals` e `DealBoard` não mudam (já somam `value`).

### 7.3 Formulário da oportunidade (`DealForm`)

- **Sem itens:** como hoje, com "Valor *" digitado e o botão "Adicionar itens" logo abaixo do valor, que abre o editor com um cartão.
- **Com itens:** o campo "Valor" dá lugar a "Valor do contrato" só leitura (o total do editor), com a dica do detalhamento; a validação do valor não se aplica.
- **Edição de uma oportunidade com itens:** lê `['crm', orgId, 'deal-items', dealId]` ao abrir; enquanto lê, o editor mostra "Carregando itens…"; se a leitura falha, mostra o erro com "Tentar novamente", e o formulário continua salvando os outros campos (os itens não foram mexidos).
- **Salvar** (C6): se os itens mudaram (comparação do rascunho com o lido) ou se é criação com itens, chama `save_deal` com os campos do formulário, a lista inteira de itens e os meses (na criação, com o id gerado ao abrir o formulário, guardado num `useRef`, para a nova tentativa usar o mesmo); senão, grava pelo caminho de hoje, sem `value` quando a oportunidade tem itens. O conflito da RPC mostra a mesma mensagem do caminho direto e mantém o formulário preenchido.
- **Remover todos os itens** numa oportunidade que tinha itens: o campo "Valor" volta, preenchido com o valor do contrato, e o salvar manda `p_items: []` com o valor do campo.
- O aviso "Descartar alterações?" passa a considerar os itens.

### 7.4 Painel da oportunidade (`DealDetail`)

- Abaixo do valor em destaque, `dealValueBreakdown` quando há itens ("R$ 1.500,00 único + R$ 2.000,00/mês × 12 meses").

O valor desta oportunidade não é calculado por itens" (para quem edita, "e pode ser mudado em “Editar”") e "Adicionar itens"; com itens, a lista só leitura (nome, quantidade e unidade, preço, desconto, cobrança e total da linha) e os totais, com "Editar itens" para quem edita.

Sucesso: "Itens salvos." e invalida `deals`, `deal-items` e `operation-references`. Conflito: a mensagem da RPC, os itens preenchidos continuam, e os dados recarregam; a versão do editor é a lida ao abrir, como no formulário (0.8): para salvar, a pessoa cancela, confere os itens atuais e edita de novo.

- O diálogo de exclusão (`DealDeleteDialog`) diz "Os itens da oportunidade são excluídos com ela." quando há itens.

### 8.2 Colunas e sinônimos (`src/lib/product-import-headers.ts`)

| Coluna do modelo | Campo | Sinônimos (sem acento, maiúscula, pontuação e asterisco) | Valores |

### 8.3 Análise, prévia e gravação (`src/lib/product-import.ts`, `CatalogImportDialog`)

- **Erros por linha**, todos os motivos juntos, com a linha do Excel: nome vazio ou longo, código longo, tipo ou cobrança desconhecidos, preço vazio, negativo, com mais de 2 casas ou em formato não reconhecido (as mensagens do `parseBRL`), unidade longa.
- **Repetidas:** código igual (aparado, sem maiúscula) ao de um item do catálogo, arquivado ou não, ou ao de uma linha anterior; sem código, nome igual (`textKey`) ao de um item sem código ou ao de uma linha anterior sem código. O motivo diz qual ("Já existe no catálogo, arquivado, com o código X."). A importação não atualiza nem reativa itens (decisão do item; a atualização por planilha fica para a 2B.1).
- **Prévia** com as contagens, as colunas reconhecidas e ignoradas e as abas "Prontas", "Repetidas" e "Com erro" (os componentes `ImportProgress` e `ImportIssues` do 1.11 ganham rótulos por parâmetro, em vez de cópias). Nada é gravado antes de "Importar {n} itens".
- **Gravação:** `upsert` em lotes de 500, com o id gerado na prévia (`onConflict: 'id'`, `ignoreDuplicates`), um lote por vez, com progresso, "Parar" e "Continuar importação" sem duplicar; um 23505 do código (cadastrado no meio por um colega) relê o catálogo e reenvia o lote sem a linha, uma vez; 42501 (o papel mudou) para e diz o motivo. O cache `['crm', orgId, 'products']` é invalidado no fim.
- **Resultado:** "Importação concluída" ou "parada", com "Baixar itens não importados" (`exportFileName('catalogo-nao-importados', 'csv')`), que pode ser corrigida e importada de novo.
- **Quem importa:** donos e administradores (a escrita em `products` é deles). O botão não aparece para os demais.

## 10. Casos de borda e corrida

| Caso | Comportamento |
| --- | --- |
| Colega edita a oportunidade (título, responsável, movimento) enquanto os itens estão abertos | A gravação dos itens encontra outra versão: conflito, nada gravado, itens mantidos na tela. |
| Duas pessoas salvam itens da mesma oportunidade ao mesmo tempo | `FOR UPDATE` enfileira; a segunda é recusada pela versão (runner). |
| Resposta perdida na criação com itens | A nova tentativa (mesmo id) devolve a oportunidade criada, `replayed`. |
| Resposta perdida na edição dos itens | A nova tentativa encontra a versão nova e mostra o conflito; ao recarregar, os itens salvos aparecem (como `complete_activity` sem próxima ação). |
| Produto arquivado entre abrir o editor e salvar | Item novo com ele é recusado com o nome; item que já o usava continua. |
| Produto excluído entre abrir e salvar | A FK recusa (23503): "Um item do catálogo usado nesta oportunidade foi excluído. Escolha outro item ou use um item avulso." |
| Preço do catálogo muda depois | Itens já gravados mantêm o preço negociado. |
| Oportunidade ganha ou perdida | Itens editáveis, como o valor hoje; os Relatórios passam a contar o novo valor. O histórico de valores fica para o 3.9. |
| Oportunidade de contato anonimizado | Editar itens passa (o contato não muda); o nome dos itens já passou pela troca de termos. |
| Responsável desativado | Editar itens passa; trocar para um desativado continua recusado (1.2). |
| Desativação ou passagem de carteira durante a gravação | As travas se enfileiram; quem vier depois vê a versão nova (conflito na tela, se for a gravação dos itens). |
| Excluir a oportunidade com itens | `delete_deal` exclui; os itens saem em cascata, auditados. |
| Mensal com preço zero | Exige meses (há item mensal); a mensalidade é 0. |
| Remover o último item mensal | Os meses somem e vão vazios. |
| 100 itens, contrato no limite | Aceitos; 101 itens ou contrato acima do limite são recusados com a mensagem. |
| Número com 4 casas, "1e3", "1,2,3", negativo | Recusados na tela (parsers) e no banco (`scale()`, `CHECK`). |
| Frontend antigo muda o valor de uma oportunidade com itens | 23514; o valor continua o do contrato. |
| Cliente tenta gravar `item_count` ou as partes | O gatilho devolve os valores antigos (ou zera na inserção). |
| Cliente tenta inserir em `deal_items` | 42501 (sem `INSERT` para `authenticated`). |
| Importação: código cadastrado por colega no meio | 23505, releitura e reenvio sem a linha (como o 1.11). |
| Importação: papel rebaixado no meio | 42501, para e diz o motivo; o que entrou fica. |
| Catálogo grande | Lido paginado; a busca do seletor é local. Catálogos de milhares de itens estão fora do público (times pequenos e médios). |

## 11. Alternativas consideradas

| Alternativa | Por que foi descartada |
| --- | --- |
| `deals.value` = só o total único, com a mensalidade à parte | Esconde a recorrência da previsão e dos ganhos; quem vende serviço mensal veria valores irreais. |
| `deals.value` = total único + 12 × mensalidade (ACV) ou + primeira mensalidade | Inventa um prazo ou subestima o contrato; o roteiro pede "mensalidade × meses informados". |
| Calcular os totais por gatilho em `deal_items` (qualquer escritor) | Uma atualização da oportunidade por instrução (exclusão e inserção dão duas), auditoria e versão renovadas mais de uma vez por gravação e gatilhos com tabelas de transição; a RPC única com a escrita da API fechada garante o mesmo com uma gravação. |
| Duas chamadas (oportunidade direto, itens pela RPC) | Gravação pela metade quando a segunda falha (campos salvos, itens não). |
| Toda gravação da oportunidade pela RPC | O frontend novo pararia de criar oportunidades num banco sem a migração, e o caminho testado desde o 0.8 mudaria sem necessidade. |
| Substituir todos os itens a cada gravação (excluir e inserir) | Ids trocados a cada gravação (o 2B.14 e o 2B.15 vão apontar para itens), auditoria com o dobro de linhas. |
| Total da linha calculado só na RPC (sem coluna gerada) | Outro escritor (SQL de manutenção, futura importação de oportunidades) poderia gravar um total incoerente. |
| Cálculo com `number` em reais na tela | Ponto flutuante ("0,1 + 0,2"); centavos inteiros, com `BigInt` na multiplicação, são exatos. |
| Meses padrão 12 | O número muda a previsão; quem vende informa o que negociou. |
| `products.active` booleano | `archived_at` diz também quando. |
| Excluir produto usado com `SET NULL` | Perde o vínculo para o 2B.14 (comissão por produto) e o 2A.1; arquivar resolve sem perder nada. |
| Quantidade inteira | Horas e quilos fracionados são comuns em serviços e produtos. |
| Bloquear os itens de oportunidades encerradas | O valor delas é editável hoje para correções; o mesmo vale para os itens. |
| Preço travado no catálogo | Vendedor negocia; o catálogo sugere. Uma matriz de permissões está fora do escopo. |
| Importação do catálogo em "Integrações" | A escrita do catálogo é de donos e administradores, e "Integrações" importa contatos para quem edita; a aba do catálogo concentra o que é do catálogo. |
| Desconto no total da oportunidade | Não pedido (D14 fala em desconto por item); fica para as propostas (2B.15), se pedido. |

## 12. Riscos

**Revisão da implementação (19/10/2026):**

18. **Itens lidos pela versão da oportunidade**: a consulta dos itens tem a chave `['crm', orgId, 'deal-items', dealId, updated_at]`. Toda gravação dos itens por `save_deal` renova a versão da oportunidade, então uma versão nova lê os itens de novo, e o editor nunca monta os rascunhos com a lista de uma versão anterior à que vai na guarda (seção 7). Antes, os itens ficavam até 5 minutos no cache enquanto a oportunidade se renovava a cada 30 segundos: a gravação mandava uma versão atual com uma lista velha e revertia os itens de um colega sem conflito.
19. **Reforço no banco** (refeito na segunda rodada, ajuste 23): a versão da oportunidade cobre também os itens. A anonimização, única escritora de itens além de `save_deal`, renova a versão das oportunidades cujos itens renomeia, e a lista lida antes cai na guarda por igualdade de `save_deal`. `dealItemsRace` (`scripts/test-database.mjs`) confere essa recusa e a trava `FOR KEY SHARE` do contato novo antes dos itens (ajuste 7), que antes não tinha teste.
20. **Criação repetida com `replayed`**: quando a primeira tentativa já tinha gravado, a tela avisa que o que mudou depois da falha não foi gravado (`DEAL_CREATE_REPLAYED`) e abre o detalhe, em vez de dizer que criou.
21. **Textos**: a dica de "Mensalidades ganhas" e o "inclui R$ X/mês × os meses" de "Ganhos por responsável" dizem que o valor ganho soma a mensalidade vezes os meses; o painel sem itens diz "Nenhum item. O valor desta oportunidade não é calculado por itens" (com "e pode ser mudado em “Editar”" para quem edita), que vale para o valor digitado, o último calculado e o das integrações; o seletor "Produto ou serviço" mostra "Sem catálogo" só quando a empresa não tem item ativo.
22. **Nomes acessíveis**: o "Valor do contrato" só leitura do formulário é um grupo (`role="group"`) com o rótulo e a explicação, e o bloco "Totais dos itens" do editor é uma `section` com o título, porque parágrafo e `div` não podem ter nome.

**Segunda rodada da revisão da implementação (19/10/2026):**

23. **Guarda dos itens sem ordem de tempo**: a primeira versão do ajuste 19 recusava a lista quando algum item tinha `updated_at` posterior à versão enviada. Só que `updated_at` vem de `now()`, o início de cada transação, que não segue a ordem dos commits: uma anonimização aberta antes da gravação de um colega deixava o item renomeado com `updated_at` menor que a versão, e a lista velha gravava de novo o nome da pessoa (LGPD); um `move_deal` aberto antes da gravação dos itens deixava a versão menor que os itens, e a oportunidade recusava toda gravação de itens até outra mudança. Agora `save_deal` só compara a versão por igualdade, e `anonymize_contact`, no passo 4, trava antes (`FOR NO KEY UPDATE`, a ordem de `save_deal`: oportunidade, depois itens) as demais oportunidades com itens que citam os termos fortes, renomeia os itens só nelas e renova a versão das que tiveram item renomeado (`touch_updated_at`; a auditoria ignora a mudança só em `updated_at`). As oportunidades da pessoa já ganham versão nova no passo 3. `dealItemsRace` ganhou os dois casos com a transação aberta antes: a anonimização (a lista velha é recusada e o nome continua anonimizado) e o `move_deal` (a gravação com a versão atual é aceita).
24. **Dica de "Mensalidades ganhas" sem corte**: o `StatStrip` corta a dica numa linha (`truncate`), e a frase de 70 caracteres aparecia pela metade em todas as larguras. A dica passou a "Já incluídas no valor ganho", e a explicação completa fica num parágrafo abaixo da faixa, só quando o número aparece (seção 6.2). O Vitest confere o tamanho da dica e o parágrafo; o E2E confere que a dica cabe sem corte (`scrollWidth <= clientWidth`) no desktop e no celular.
