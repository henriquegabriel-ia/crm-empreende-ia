Fontes consultadas em **19/10/2026**:

- GitHub, [planos](https://docs.github.com/en/get-started/learning-about-github/githubs-plans): o GitHub Free para organizações tem repositórios privados ilimitados, colaboradores ilimitados e 2.000 minutos do Actions por mês para repositórios privados; o excedente é cobrado da conta.
- GitHub Actions: o contexto `vars` vale na condição `if` de um job; filtros `paths-ignore` valem para o evento inteiro do workflow, e não por job (por isso a conferência da distribuição fica num workflow próprio); agendamentos (`schedule`) rodam em repositórios privados criados por clone (só são desligados sozinhos em repositórios públicos sem atividade há 60 dias, e por padrão não rodam em forks).

- Git: `git init -b <branch>` (Git 2.28 ou mais); `GIT_CONFIG_GLOBAL` e `GIT_CONFIG_NOSYSTEM` isolam a configuração pessoal de um comando; `git ls-files -z --cached --others --exclude-standard` lista os arquivos versionados e os novos ainda não ignorados; histórias sem ancestral comum só se juntam com `--allow-unrelated-histories`.

## 4. O repositório de distribuição

### 4.1 Forma

| Aspecto | Escolha |
| --- | --- |
| Onde | Organização GitHub do programa (D5), repositório **privado**, criado vazio pelo `@devops`. O nome e a organização ficam no registro do ambiente do dono. |
| Branch | `main`, só ele. |
| Commits | Um por versão, `chore: versão X.Y.Z`, autor e committer da identidade do programa (`--author`). Nunca reescrito: versão com problema se corrige com a seguinte. |
| Tags | `vX.Y.Z` anotada, no commit da versão, criada e enviada só pelo `@devops`. |
| Variável | `CRM_DISTRIBUTION_REPOSITORY=true` (Settings → Secrets and variables → Actions → Variables). Nunca `CRM_BASE_REPOSITORY`, para o noturno não rodar ali. |
| Acesso | Alunos da turma com leitura (um time da organização). Forks desligados ("Allow forking"): o guia manda clonar para um repositório da empresa, e um fork privado some quando o aluno perde o acesso. |
| Visibilidade | Privado sempre: a `LICENSE` proíbe repositório público. |

### 4.2 Por que um histórico por cima do outro

O aluno clona a distribuição e registra `upstream` (etapa 1 do guia de implantação); depois, atualiza com `git fetch upstream --tags` e `git merge vX.Y.Z` (etapa 4 do guia de atualização). O merge só funciona se `vX.Y.Z` descende do commit que o aluno clonou. Por isso cada versão é gerada sobre o clone do repositório de distribuição, e nunca num `git init` novo (que daria histórias sem ancestral comum e "refusing to merge unrelated histories").

## 5. `npm run release:dist`

### 5.1 Uso

```
npm run release:dist -- --out <pasta> --author "Nome <e-mail>" [--rehearsal] [--verify] [--e2e]
npm run release:dist -- --list
```

- `--out` é obrigatório (sem padrão): uma pasta que não existe, uma pasta vazia (primeira versão) ou um clone do repositório de distribuição (versões seguintes).
- `--author` é obrigatório fora do `--list`, no formato `Nome <e-mail>`; o e-mail não pode ser um termo pessoal (seção 7.3). Sem padrão, para não inventar a identidade do programa.
- `--list` só mostra a classificação (incluídos, excluídos com o motivo, não classificados) e sai com 1 se houver não classificado.
- `--verify` roda na pasta gerada, em sequência e parando na primeira falha: `npm ci`, `release:check --dist .`, e os passos do job Qualidade (`format:check`, `docs:links`, `lint:ci`, `typecheck`, `npm test`, `test:db`, `gen:types:check`, `manifest:check`, `emails:check`, `build`), com `CRM_DISTRIBUTION_REPOSITORY=true`. `--e2e` acrescenta `test:e2e` (portas 8096, 8098 e 8099: nunca ao mesmo tempo que o E2E do repositório da base). `npm ci` só roda na pasta gerada, nunca no repositório da base.

### 5.2 Passos

1. **Base.** Lê `package.json` e `CHANGELOG.md`. No modo real: a pasta de trabalho limpa (`git status --porcelain` vazio), a versão publicada (não termina em `.0` de pré-versão e é a primeira versão com data do `CHANGELOG.md`, pelas regras de `changelog.mjs`) e o registro do ambiente do dono presente com o ref (a distribuição só sai do repositório da base).
2. **Arquivos.** `git ls-files -z --cached --others --exclude-standard`, sem os que não existem mais na pasta. Recusa link simbólico (modo `120000`) e submódulo (`160000`) e arquivo acima de 2 MB. Classifica (seção 6): não classificado, padrão perigoso ou arquivo proibido reprova.
3. **Conteúdo.** As regras da seção 7.2 sobre os arquivos incluídos, com os termos privados. Reprovado, nada é escrito.
4. **Pasta de destino.** As recusas da seção 5.3. Primeira versão: cria a pasta. Versão seguinte: remove da pasta os arquivos versionados dela (`git ls-files` da distribuição), nunca a pasta `.git`.
5. **Cópia.** Os bytes de cada arquivo incluído, com o caminho relativo (o `.gitattributes` da base garante LF na pasta de trabalho; no modo real ela é igual ao commit).
6. **Commit.** `git` com `GIT_CONFIG_GLOBAL` apontando para um arquivo vazio temporário, `GIT_CONFIG_NOSYSTEM=1`, `-c user.name`/`-c user.email` do `--author` (autor e committer), `-c core.autocrlf=false`. Primeira versão: `git init -b main` (com o recuo `git symbolic-ref HEAD refs/heads/main` no Git anterior ao 2.28). `git add -A` e `git commit -m "chore: versão X.Y.Z" -m "Base do CRM. O que mudou e o que fazer ao atualizar: CHANGELOG.md."`. No ensaio, a mensagem é `ensaio: X.Y.Z (não publicar)`.
7. **Resumo.** Versão, quantidade de arquivos e tamanho, o commit da base de origem, a pasta e os próximos passos do `@devops` (seção 10, passos 5 a 8), com a lembrança de que o script não envia nem cria tag. Com `--verify`, os passos e o resultado de cada um.

### 5.3 Recusas (todas antes de escrever)

| --- | --- |

### 5.4 O ensaio

O `package.json` está em `1.0.0-beta.0` até o commit de lançamento, que é do `@devops` com a confirmação do dono (pendências do 1.7b). ## 6. A allowlist

### 6.1 Forma

Em `scripts/lib/distribution.mjs`, três listas congeladas de padrões no formato do Git (`/` como separador, `*` dentro de uma pasta, `**` em qualquer profundidade), interpretados por uma função própria e testada (sem dependência nova; `path.matchesGlob` não existe no Node 20):

- `DISTRIBUTION_ALLOWLIST`: `{ pattern, reason }`. Arquivos da raiz e documentos sempre por nome; pastas de código por padrão.
- `DISTRIBUTION_EXCLUDED`: `{ pattern, reason }`.
- `FORBIDDEN_PATHS`: o que nunca pode ser distribuído, mesmo que alguém o acrescente à allowlist.

Regras da classificação: (1) cada arquivo casa com a allowlist ou com os excluídos, nunca com os dois; (2) nenhum arquivo incluído casa com `FORBIDDEN_PATHS`; (3) nenhum padrão da allowlist alcança um caminho proibido de exemplo (`docs/**` reprovaria por alcançar a pasta do dono; a conferência testa cada padrão contra uma lista de caminhos-sentinela); (4) cada padrão sem curinga corresponde a um arquivo que existe (allowlist desatualizada reprova); (5) os `REQUIRED_FILES` estão incluídos.

## 7. `npm run release:check` (a conferência contra vazamento)

### 7.1 Uso e escopo

```
npm run release:check                # o repositório atual (os arquivos incluídos pela allowlist)
npm run release:check -- --dist <pasta>   # uma árvore gerada, antes do envio
```

Só módulos do Node e o `git` (o workflow não roda `npm ci`). Sai com 0 ou com 1 e a lista `arquivo:linha — regra`. No modo `--dist`, além das regras de conteúdo: todo arquivo versionado da pasta está na allowlist; o histórico tem só commits `chore: versão …`, com autor e committer iguais entre si e fora dos termos pessoais; a versão do topo é a do `package.json`.

## 14. Casos de borda e corrida

- **Duas execuções ao mesmo tempo na mesma pasta:** a segunda encontra a pasta não vazia (primeira vez) ou o `index.lock` do Git (versão seguinte) e para; nada é removido antes das recusas.
- **Interrupção no meio:** primeira vez, a pasta sobra sem commit e a próxima execução recusa "pasta não vazia" com a instrução de apagar; versão seguinte, sobra a pasta com mudanças, e a recusa manda `git reset --hard` e `git clean -fd` nela.
- **Arquivo apagado mas ainda versionado, ou novo sem commit:** o modo real exige a pasta limpa; o ensaio usa o que está na pasta (o novo entra se a allowlist o cobre, o apagado não entra).
- **Nomes com espaço, acento ou maiúsculas:** `-z` no `git ls-files` (sem `core.quotepath`), comparação de padrões sensível a maiúsculas, como a hospedagem.
- **Fim de linha:** `.gitattributes` com LF vai junto; `core.autocrlf=false` no commit; a cópia preserva os bytes.
- **Personalização do dono na pasta de trabalho** (`.env.local`, `dist/` com a URL dele): não são versionados nem passam pela allowlist.
- **Configuração pessoal do Git** (e-mail, assinatura, hooks, `init.templateDir`): isolada no commit (AC-4); assinar a versão, se o programa quiser, é a tag do `@devops` com uma chave do programa.
- **Versão sem a seção dela no `CHANGELOG.md`:** o modo real recusa (seção 5.2); o teste do `CHANGELOG.md` já reprova o `package.json` divergente.
- **Termo pessoal que é palavra comum:** só nomes com duas palavras ou usuários longos; o dono pode retirar uma linha da tabela dele; um falso positivo de e-mail se resolve trocando o exemplo por um domínio reservado.
- **Repositório da base sem histórico completo** (checkout raso): os termos do histórico ficam incompletos; o workflow usa `fetch-depth: 0`, e a falta do ref já reprova na base.
- **Aluno roda `release:check` no clone:** reprova os arquivos dele (não classificados); é ferramenta da base, e o `AGENTS.md` diz isso.
- **Aluno que já tinha clonado e recebe `vX.Y.Z+1`:** histórico contínuo (seção 4.2); o merge segue o guia de atualização.
- **Aba aberta durante uma publicação, depois do achado 3:** sem relógio, o sono do computador ou o ajuste de hora não mudam a decisão.

## 16. Alternativas consideradas

| Alternativa | Por que foi descartada |
| --- | --- |
| Lista de exclusão no lugar da allowlist | Um arquivo novo esquecido iria para os alunos; a especificação pede allowlist. A classificação total (R3) dá a mesma comodidade sem o risco. |
| Reescrever o histórico da base (`git filter-repo`, squash) e entregar o mesmo repositório | Mexe no repositório de trabalho do dono, mantém o risco de enviar o branch errado e não resolve os autores pessoais dos commits futuros. |
| Branch órfão no repositório da base enviado ao de distribuição | Mistura os dois históricos no mesmo repositório: um `git push` com o branch errado vaza tudo. |
| Repositório "template" do GitHub ou zip a cada versão | Cada cópia nasce sem ancestral comum: o `upstream` e o `git merge vX.Y.Z` da D5 não funcionam. |
| Fork do repositório de distribuição pelo aluno | Fica ligado à organização do programa e some quando o aluno perde o acesso; a D5 e o guia pedem um repositório da empresa. |
| Transformar os documentos na hora de distribuir (tirar links, reescrever trechos) | A árvore distribuída deixaria de ser a testada; os problemas ficariam escondidos na base. A correção na origem, com a conferência no CI, é mais simples e auditável. |
| Não distribuir `docs/arquitetura/` e o roteiro | Seção 6.3. |
| Termos pessoais num arquivo distribuído, ou como hash | Escrever o termo é o vazamento; o hash seria conferível por quem já conhece o e-mail e acrescentaria complexidade. O histórico e o registro do ambiente bastam na base, onde a conferência importa. |
| Usar `CRM_BASE_REPOSITORY` também no repositório de distribuição | O noturno rodaria ali todo dia, gastando a cota da organização sem nada novo para testar. |
| Criar a tag no script | Tag é do `@devops` (Agent Authority); o script imprime o comando. |
| Comparar relógios mais precisos no achado 3 (`timeOrigin + now()`) | Cada processo do navegador calcula a própria origem, e o relógio monotônico pode parar no sono; a marca consumida não depende de hora nenhuma. |
| Pôr o endereço do repositório nos guias | R10. |
